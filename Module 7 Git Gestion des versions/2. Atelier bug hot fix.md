## Atelier 2 — Gitflow & Automatisation CI/CD

**Niveau débutant-intermédiaire · Durée : 90 min · Atelier 2/2 · Prérequis : Atelier 1**

---

## Objectif

À la fin de cet atelier vous savez :

- gérer un bug urgent sans perturber le développement en cours
- travailler avec deux environnements Dev et Prod
- déclencher automatiquement un déploiement via un pipeline CI/CD

---

## Rappel de l'architecture

```
feature/xyz  →  dev  →  main (Prod)
hotfix/xyz   →  main (Prod) → merge back dev
```

---

## Bloc 1 — Deux environnements Dev et Prod (20 min)

### 1.1 — Comprendre la stratégie de branches

Jusqu'ici vous avez travaillé avec une seule branche `main`. En entreprise il existe généralement deux branches permanentes :

| Branche | Rôle                   | Workspace Fabric |
| ------- | ---------------------- | ---------------- |
| `dev`   | Développement en cours | Fabric-Lab-Dev   |
| `main`  | Production stable      | Fabric-Lab-Prod  |

### 1.2 — Créer la branche dev

Le formateur crée la branche `dev` depuis `main` :

**Azure DevOps → Repos → Branches → New branch**

```
Name   : dev
Based  : main
```

Vous récupérez la branche `dev` en local :

```bash
git checkout main
git pull origin main
git checkout -b dev origin/dev
git branch
```

```
✓ Deux branches visibles : main et dev
✓ Vous êtes sur la branche dev
```

## Bloc 2 — Scénario 1 · Push direct sur main (15 min)

> Ce scénario est uniquement pour comprendre le déclenchement CI/CD. En équipe réelle on passe toujours par une PR.

### 2.1 — Modifier et pousser directement

```bash
git checkout main

# Faire une modification simple
echo "version 1.0" >> README.md

git add README.md
git commit -m "docs: version 1.0"
git push origin main
```

Allez dans **Azure DevOps → Pipelines** et observez :

```
✓ Le pipeline se déclenche automatiquement
✓ Les logs montrent Token obtenu avec succès
✓ Les logs montrent Déploiement Fabric déclenché
✓ Fabric-Lab-Prod est synchronisé
```

> **À retenir** : tout push sur `main` déclenche automatiquement le déploiement en production. C'est puissant mais risqué sans validation — d'où l'importance des Pull Requests.

## Bloc 3 — Scénario 2 · Feature → dev → main (30 min)

C'est le workflow quotidien en équipe.

### 3.1 — Créer une feature depuis dev

```bash
git checkout dev
git pull origin dev

# Créer une branche feature depuis dev
git checkout -b feature/ajout-transformation

# Faire une modification
echo "transformation dataset v2" >> README.md

git add README.md
git commit -m "feat: ajout transformation dataset v2"
git push origin feature/ajout-transformation
```

### 3.2 — PR feature → dev

**Azure DevOps → Repos → Pull Requests → New Pull Request**

```
Source : feature/ajout-transformation
Target : dev
Titre  : feat: ajout transformation dataset v2
```

Le formateur approuve → vous mergez.

```
✓ Pipeline dev déclenché automatiquement
✓ Workspace Fabric-Lab-Dev synchronisé
✓ Vous validez le résultat dans Fabric-Lab-Dev
```

### 3.3 — PR dev → main

Une fois validé dans Dev, vous promouvez vers la production :

**Azure DevOps → Repos → Pull Requests → New Pull Request**

```
Source : dev
Target : main
Titre  : release: promotion dev vers main
```

Le formateur approuve → vous mergez.

```
✓ Pipeline main déclenché automatiquement
✓ Workspace Fabric-Lab-Prod synchronisé
✓ Vous validez le résultat dans Fabric-Lab-Prod
```

> **À retenir** : deux PR, deux validations, deux déploiements automatiques. Votre code passe par Dev avant d'aller en Prod — jamais directement.

## Bloc 4 — Scénario 3 · Bugfix urgent (25 min)

Un bug est détecté en production. Vous devez le corriger immédiatement sans toucher au développement en cours sur `dev`.

### 4.1 — Simuler le bug

Le formateur introduit volontairement une erreur dans un fichier sur `main` :

```bash
# Côté formateur uniquement
git checkout main
echo "ERREUR VOLONTAIRE" >> README.md
git add README.md
git commit -m "bug: erreur introduite pour l'exercice"
git push origin main
```

### 4.2 — Créer une branche hotfix depuis main

```bash
# Toujours depuis main — jamais depuis dev
git checkout main
git pull origin main
git checkout -b hotfix/correction-erreur
```

### 4.3 — Corriger le bug

Ouvrez `README.md` et supprimez la ligne `ERREUR VOLONTAIRE`.

```bash
git add README.md
git commit -m "fix: correction erreur production"
git push origin hotfix/correction-erreur
```

### 4.4 — PR hotfix → main

**Azure DevOps → Repos → Pull Requests → New Pull Request**

```
Source : hotfix/correction-erreur
Target : main
Titre  : fix: correction urgente production
```

Le formateur approuve → vous mergez.

```
✓ Pipeline main déclenché automatiquement
✓ Bug corrigé en production
✓ Fabric-Lab-Prod synchronisé
```

### 4.5 — Merge back hotfix → dev

**Étape critique** — vous devez reporter le fix sur `dev` pour que les deux branches restent cohérentes :

```bash
git checkout dev
git pull origin dev

# Merger le hotfix dans dev
git merge main

# Vérifier qu'il n'y a pas de conflits
git status

# Pousser dev mis à jour
git push origin dev
```

```
✓ La branche dev contient maintenant le fix
✓ main et dev sont synchronisés
✓ Aucun risque de régression au prochain merge dev → main
```

> **À retenir** : un hotfix part toujours de `main`, va vers `main`, puis est reporté sur `dev`. Sans le merge back, la prochaine release depuis `dev` écraserait votre correction.

## Récapitulatif — Les trois scénarios maîtrisés

| Scénario         | Quand                   | Flux                                 |
| ---------------- | ----------------------- | ------------------------------------ |
| Push direct main | Démo · jamais en équipe | `main` → pipeline → Prod             |
| Feature complète | Développement normal    | `feature` → `dev` → `main`           |
| Bug urgent       | Correction production   | `hotfix` → `main` → merge back `dev` |

| `git checkout -b dev origin/dev`  | Récupérer une branche distante       |
| `git merge main`                  | Merger main dans la branche courante |
| `git log --oneline --graph --all` | Visualiser toutes les branches       |

---

## Ce que Fabric fait automatiquement

À chaque merge sur `main` ou `dev` le pipeline CI/CD :

```
1. S'authentifie via le Service Principal
2. Appelle l'API Fabric
3. Synchronise le workspace correspondant
4. Vos notebooks et pipelines Fabric sont à jour
```

Vous n'intervenez plus manuellement dans Fabric — Git est la source de vérité.
