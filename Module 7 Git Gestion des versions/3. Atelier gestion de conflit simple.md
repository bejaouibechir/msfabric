## Atelier 3 — Gestion des conflits Git

**Niveau débutant · Durée : 45 min · Atelier 3/3 · Prérequis : Atelier 1**

---

## Objectif

À la fin de cet atelier vous savez :

- comprendre ce qu'est un conflit Git
- identifier un conflit et lire ce que Git vous dit
- résoudre un conflit simple
- décrire clairement la situation à un collègue plus expérimenté si besoin

---

## C'est quoi un conflit ?

Un conflit survient quand **deux personnes modifient la même ligne du même fichier** en même temps sur des branches différentes. Git ne sait pas laquelle des deux versions garder — il vous demande de choisir.

> Ce n'est pas une erreur. C'est Git qui fait son travail correctement en refusant de décider à votre place.

---

## Visualiser ce qui se passe

```
main     :  ligne modifiée par le formateur  ──────┐
                                                    ├──► CONFLIT
feature  :  même ligne modifiée par vous    ────────┘
```

Git met les deux versions en face à face et attend votre décision.

---

## Bloc 1 — Provoquer un conflit (10 min)

On va volontairement créer un conflit pour comprendre comment il se présente.

**Le formateur modifie `README.md` sur `main` :**

```bash
# Côté formateur
git checkout main
# Modifier la première ligne de README.md
# Remplacer par : "Projet Fabric - version formateur"
git add README.md
git commit -m "docs: modification formateur sur main"
git push origin main
```

**Vous modifiez le même fichier sur votre branche :**

```bash
git checkout -b feature/conflit-test
# Modifier la MÊME première ligne de README.md
# Remplacer par : "Projet Fabric - version participant"
git add README.md
git commit -m "docs: modification participant sur feature"
git push origin feature/conflit-test
```

---

## Bloc 2 — Rencontrer le conflit (10 min)

Vous ouvrez une Pull Request comme d'habitude :

**Azure DevOps → Repos → Pull Requests → New Pull Request**

```
Source : feature/conflit-test
Target : main
```

Azure DevOps affiche immédiatement :

```
⚠ This pull request has conflicts that must be resolved
   before it can be completed.
```

> **C'est normal.** Ne paniquez pas. Git vous dit simplement : deux versions du même endroit existent, choisissez laquelle garder.

Maintenant résolvez le conflit en local :

```bash
git checkout feature/conflit-test
git pull origin main
```

Git s'arrête et affiche :

```
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

Vérifiez quels fichiers sont en conflit :

```bash
git status
```

```
both modified : README.md
```

---

## Bloc 3 — Lire et résoudre le conflit (15 min)

Ouvrez `README.md` dans votre éditeur. Git a marqué le conflit ainsi :

```
<<<<<<< HEAD (votre branche feature)
Projet Fabric - version participant
=======
Projet Fabric - version formateur
>>>>>>> main
```

**Comment lire ces marqueurs :**

| Marqueur       | Signification                      |
| -------------- | ---------------------------------- |
| `<<<<<<< HEAD` | Début de votre version             |
| `=======`      | Séparateur entre les deux versions |
| `>>>>>>> main` | Fin de la version de main          |

**Vous avez trois choix :**

**Choix 1 — Garder votre version :**

```
Projet Fabric - version participant
```

**Choix 2 — Garder la version main :**

```
Projet Fabric - version formateur
```

**Choix 3 — Combiner les deux :**

```
Projet Fabric - version participant et formateur
```

Pour cet exercice choisissez le **Choix 3** — supprimez les marqueurs Git et gardez :

```
Projet Fabric - version participant et formateur
```

Le fichier ne doit plus contenir aucun marqueur `<<<<<<<`, `=======`, `>>>>>>>`.

Sauvegardez puis :

```bash
# Marquer le conflit comme résolu
git add README.md

# Vérifier qu'il n'y a plus de conflit
git status

# Commiter la résolution
git commit -m "fix: résolution conflit README main vs feature"

# Pousser
git push origin feature/conflit-test
```

Retournez dans Azure DevOps — la PR affiche maintenant :

```
✓ No conflicts — prête à merger
```

```
✓ Merger la PR normalement
```

## Bloc 4 — Savoir décrire la situation (10 min)

Parfois le conflit est trop complexe pour être résolu seul. L'essentiel est de savoir **décrire clairement ce qui se passe** à un collègue plus expérimenté.

**Commandes pour collecter les informations utiles :**

```bash
# Quels fichiers sont en conflit
git status

# Voir l'historique des deux branches
git log --oneline --graph --all

# Voir exactement ce qui diffère
git diff
```

**Le message type à envoyer à votre admin ou collègue :**

```
Bonjour,

J'ai un conflit Git sur ma branche feature/conflit-test
lors du merge vers main.

Fichier concerné : README.md
Ma branche modifie : ligne 1
La branche main modifie : ligne 1 également

Résultat de git status :
both modified : README.md

Je n'arrive pas à identifier laquelle des deux versions
garder sans risquer de perdre du travail.
Pouvez-vous m'aider ?
```

> Un collègue expérimenté qui reçoit ce message a **toutes les informations** pour vous aider immédiatement sans poser de questions supplémentaires.

---

## Ce qu'il faut retenir

**Un conflit c'est :**

```
✓ Normal — ça arrive à tout le monde
✓ Pas une erreur de votre part
✓ Git qui refuse de choisir à votre place
✓ Toujours localisé dans un fichier précis sur des lignes précises
```

**Les trois marqueurs à reconnaître :**

```
<<<<<<< votre branche
votre version
=======
leur version
>>>>>>> main
```

**La règle d'or :**

```
Supprimer les marqueurs · garder ce qui est juste · git add · git commit
```

**Si vous bloquez :**

```
git status        → identifier les fichiers en conflit
git diff          → voir exactement ce qui diffère
git log --oneline --graph --all  → comprendre l'historique
→ décrire la situation clairement à un collègue
```

---

**Vous n'avez pas besoin de tout résoudre seul. Savoir identifier, décrire et demander de l'aide au bon moment est une compétence professionnelle à part entière.**
