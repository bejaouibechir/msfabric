## Scénario 1 — Switch branch et Checkout new branch

**But pédagogique** : comprendre la différence entre basculer sur une branche existante et en créer une nouvelle depuis Fabric.

### 1.1 — Switch branch (basculer sur une branche existante)

Connecté en tant que **dev** dans le workspace **`EN-FAB-DEV-GitCICD`** :

1. Cliquer sur le bouton **Source control** dans la barre du workspace
2. En haut du panneau, vérifier que la branche courante est **`main`**
3. Cliquer sur le menu déroulant de la branche courante
4. Sous **Current workspace**, sélectionner **Switch branch**
5. Choisir une autre branche existante (ex. une branche feature si elle existe)
6. Cliquer **Switch**

**Ce que vous devez voir à l'écran** :

- le nom de la branche dans le panneau passe à `main`
- les items du workspace reflètent l'état de `main`

> 💡 **Astuce** : switcher sur `main` revient à voir l'état "validé et stable" du projet. Aucun développement en cours n'y apparaît.

⚠️ **Piège** : si des modifications non commitées sont en attente dans `develop`, Fabric affiche un avertissement. Il faut committer ou annuler avant de switcher.

---

### 1.2 — Checkout new branch (créer et basculer sur une nouvelle branche)

1. Cliquer sur le bouton **Source control** dans la barre du workspace (en haut à gauche)
2. Le panneau **Source control** s'ouvre sur la droite — la branche courante apparaît sous **Current branch**
3. Cliquer sur le menu déroulant de la branche courante pour afficher les options
4. Sous la section **Current workspace**, cliquer **Checkout new branch**
5. Renseigner :

| Champ           | Valeur             |
| --------------- | ------------------ |
| **Branch name** | `test/demo-switch` |
| **Based on**    | `main`             |

6. Cliquer **Create and switch**

**Ce que vous devez voir à l'écran** :

- la branche active devient `test/demo-switch`
- la branche est également visible dans GitHub → dépôt `testgitmsfabric`

> 💡 **Note sur le menu** : deux sections sont disponibles dans le panneau Source control :
> 
> - **Other workspaces** → **Branch out to workspace** (crée un workspace séparé lié à une nouvelle branche)
> - **Current workspace** → **Checkout new branch** / **Switch branch** (agit sur le workspace courant)

> 💡 **Différence clé** :
> 
> - **Switch branch** → aller sur une branche qui **existe déjà**
> - **Checkout new branch** → **créer** une branche ET y basculer immédiatement

7. Revenir sur `main` via **Switch branch** avant de continuer la suite de l'atelier

> ⚠️ **Ne pas supprimer** la branche `test/demo-switch` depuis GitHub tant que le workspace Fabric y est encore connecté. Supprimer la branche distante alors que Fabric pointe dessus provoque une désynchronisation et bloque les commits suivants. Supprimer uniquement après avoir switché sur `main`.

## Scénario 2 — Branche feature et Pull Request

**But pédagogique** : isoler une évolution fonctionnelle, collaborer entre deux comptes, et valider les changements via une Pull Request GitHub.

### Contexte métier

L'équipe souhaite ajouter une **alerte de surcharge** dans le notebook de transformation : tout équipement dont le `LoadPct` dépasse 95 % doit être marqué `OVERLOAD`.

> 💡 **Note sur les permissions** : avec le rôle **Contributor**, les options **Checkout new branch** et **Switch branch** sont grisées. Seule l'option **Branch out to workspace** est disponible. C'est donc cette option que le participant doit utiliser — elle crée une nouvelle branche **et** un nouveau workspace dédié à la feature.

Se connecter avec le compte **participant** sur [https://app.fabric.microsoft.com](https://app.fabric.microsoft.com) :

1. Ouvrir le workspace **`EN-FAB-DEV-GitCICD`**

- ce workspace est connecté à la branche `feature/overload-alert`

⚠️ **Piège** : le participant travaille désormais dans le **nouveau workspace**, pas dans `EN-FAB-DEV-GitCICD`. C'est dans `EN-FAB-DEV-Feature-Overload` qu'il faut ouvrir les notebooks pour la suite.

---

### 2.3 — participant ajoute la fonctionnalité

Toujours connecté en tant que **participant**, dans le workspace **`EN-FAB-DEV-Feature-Overload`** :

1. Ouvrir le notebook **`nb_02_transform_equipment_health`**
2. Ajouter une **nouvelle cellule** après la cellule de transformation existante :

```python
# Feature: OVERLOAD alert when LoadPct > 95%
from pyspark.sql.functions import col, when, lit

health_df = health_df.withColumn(
    "HealthStatus",
    when(col("LoadPct") > 95, lit("OVERLOAD")).otherwise(col("HealthStatus"))
)

health_df.write.mode("overwrite").format("delta").saveAsTable("gold_equipment_health")

display(
    health_df.select("EquipmentId", "EquipmentName", "LoadPct", "HealthStatus")
             .orderBy("LoadPct", ascending=False)
)
```

3. Exécuter la cellule pour valider qu'elle fonctionne

**Ce que vous devez voir à l'écran** :

- les équipements triés par `LoadPct` décroissant
- les éventuels équipements en `OVERLOAD` apparaissent en premier

---

## Scénario 3 — Branche bugfix

**But pédagogique** : isoler une correction métier identifiée et montrer comment la réparer via Git depuis Fabric.

### Contexte métier

Un utilisateur signale que l'équipement **EQ-WT-003** (Turbine Nord 3, vibration = 6.7 mm/s) est classé `NORMAL` alors qu'il devrait être en `WARNING`. En relisant le code, on constate que le seuil d'alerte vibration est fixé à 75 % du seuil critique — trop permissif. Le seuil métier correct est **80 %**.

---

### 3.1 — Créer la branche bugfix

Connecté en tant que **dev** dans Fabric :

1. Ouvrir le panneau **Source control** sur la branche `develop`
2. Cliquer sur le nom de la branche → **Checkout new branch**
3. Renseigner :

| Champ           | Valeur                               |
| --------------- | ------------------------------------ |
| **Branch name** | `bugfix/vibration-warning-threshold` |
| **Based on**    | `develop`                            |

4. Cliquer **Create and switch**

---

### 3.2 — Corriger le notebook

1. Ouvrir **`nb_02_transform_equipment_health`**
2. Localiser le bloc `VibrationStatus` et remplacer :

```python
# AVANT (seuil trop permissif)
.when(col("VibrationMmS") >= col("CriticalVibrationMmS") * 0.75, lit("WARNING"))
```

par :

```python
# APRÈS (seuil métier corrigé)
.when(col("VibrationMmS") >= col("CriticalVibrationMmS") * 0.80, lit("WARNING"))
```

3. Exécuter le notebook complet
4. Vérifier qu'EQ-WT-003 (vibration 6.7, seuil critique 8 → 80 % = 6.4) passe bien en `WARNING`

---

### 3.3 — Committer et ouvrir la PR

1. Dans le panneau **Source control**, commiter avec le message :

```text
bugfix: correct vibration WARNING threshold from 75% to 80%
```

2. Sur GitHub, ouvrir une Pull Request de `bugfix/vibration-warning-threshold` → `develop`
3. **dev** (ou le même compte) review et merge
4. Revenir dans Fabric sur `develop` → **Update all**

> 💡 **Bonne pratique** : même pour un bugfix simple, passer par une PR permet de tracer la décision et de garder un historique lisible dans GitHub.

## Scénario 4 — Hotfix

**But pédagogique** : simuler une correction urgente directement sur `main` (équivalent production), puis la réintégrer dans `develop` pour ne pas perdre la correction.

### Contexte métier

Une erreur critique est détectée : le chemin de fichier dans le notebook d'ingestion a été modifié par erreur (`energie` au lieu de `energy`). Le pipeline échoue. Correction immédiate requise sans attendre le cycle normal de `develop`.

---

### 4.1 — Créer la branche hotfix depuis main

Connecté en tant que **dev** dans Fabric :

1. Switcher sur la branche **`main`** via **Source control → Switch branch**
2. Créer une nouvelle branche :

| Champ           | Valeur                  |
| --------------- | ----------------------- |
| **Branch name** | `hotfix/fix-input-path` |
| **Based on**    | `main`                  |

---

### 4.2 — Appliquer le correctif

1. Ouvrir **`nb_01_ingest_energy_files`**
2. Corriger les chemins :

```python
# AVANT (erroné)
readings_path  = "Files/input/energie/equipment_readings.csv"
reference_path = "Files/input/energie/equipment_reference.csv"

# APRÈS (corrigé)
readings_path  = "Files/input/energy/equipment_readings.csv"
reference_path = "Files/input/energy/equipment_reference.csv"
```

3. Exécuter le notebook pour confirmer que les tables se recréent correctement

---

### 4.3 — Merger le hotfix dans main ET dans develop

**Merger dans main :**

1. Commiter avec le message :

```text
hotfix: restore correct input path Files/input/energy/
```

2. Sur GitHub, ouvrir une PR de `hotfix/fix-input-path` → `main`
3. Merger immédiatement

**Réintégrer dans develop :**

4. Sur GitHub, ouvrir une **seconde PR** de `hotfix/fix-input-path` → `develop`
5. Merger

> 💡 **Règle d'or du hotfix** : tout ce qui est mergé dans `main` doit aussi remonter dans `develop`. Sans cette étape, la correction sera écrasée lors du prochain déploiement.

6. Dans Fabric, revenir sur `develop` → **Update all**
7. Supprimer la branche `hotfix/fix-input-path` sur GitHub

## Scénario 5 — Conflit de version entre Fabric et GitHub

**But pédagogique** : comprendre comment un conflit survient et comment le résoudre proprement.

### Comment le conflit se produit

**dev** et **participant** sont tous deux sur `develop`. Ils modifient le même notebook en même temps. Le premier qui commite "gagne" ; le second se retrouve en conflit.

---

### 5.1 — Reproduire le conflit

**Étape A** — connecté en tant que **participant** dans Fabric :

1. Ouvrir `nb_02_transform_equipment_health`
2. Ajouter à la fin de la première cellule :

```python
print("Modif participant - develop")
```

3. **Ne pas commiter encore**

**Étape B** — connecté en tant que **dev** sur GitHub (éditeur web) :

1. Aller dans `testgitmsfabric` → branche `develop` → dossier `/fabric`
2. Ouvrir le fichier de définition JSON du notebook `nb_02_transform_equipment_health`
3. Ajouter un commentaire dans le code (ex. `# dev edit via GitHub`)
4. Commiter directement sur `develop` avec le message :

```text
chore: dev edit nb_02 via GitHub
```

**Étape C** — revenir dans Fabric (**participant**) :

1. Tenter de commiter les changements de l'étape A
2. Fabric affiche un avertissement : **"Remote branch is ahead"** ou **"Conflict detected"**

---

### 5.2 — Résoudre le conflit

**Option 1 — Update puis recommit (recommandée)** :

1. Dans le panneau **Source control**, cliquer **Update all**
2. Fabric applique les changements distants sur le workspace
3. Vérifier manuellement que les modifications de **participant** sont toujours présentes dans le notebook
4. Si tout est cohérent, commiter à nouveau

**Option 2 — Résolution via GitHub** :

1. Sur GitHub, naviguer dans la branche en conflit
2. Cliquer **Resolve conflicts**
3. Dans l'éditeur, conserver les deux changements ou choisir la version correcte
4. Cliquer **Mark as resolved** → **Commit merge**
5. Dans Fabric, cliquer **Update all** pour récupérer la version résolue

> 💡 **Bonne pratique** : toujours faire **Update all** avant de commencer à modifier des items, surtout en contexte multi-contributeurs.

⚠️ **Piège** : les définitions des notebooks Fabric sont des fichiers JSON. Ne pas modifier leur structure manuellement sans comprendre le format, au risque de corrompre le notebook lors de la resynchronisation.

## Scénario 6b — Deployment Rules : schéma DEV vs PROD

**But pédagogique** : montrer comment une Deployment Rule change automatiquement un paramètre lors du déploiement, ici le schéma cible des tables Delta (`dev` en DEV, `prod` en PROD).

### Contexte

| Workspace             | Lakehouse       | Schéma utilisé |
| --------------------- | --------------- | -------------- |
| `EN-FAB-DEV-GitCICD`  | `lh_energy_ops` | `dev`          |
| `EN-FAB-PROD-GitCICD` | `lh_energy_ops` | `prod`         |

Les deux schémas ont été créés via T-SQL dans le SQL analytics endpoint :

```sql
CREATE SCHEMA dev;
CREATE SCHEMA prod;
```

---

### 6b.1 — Modifier nb_01_ingest_energy_files

1. Ouvrir **`nb_01_ingest_energy_files`**
2. Ajouter une **nouvelle cellule tout en haut** du notebook
3. Tagger cette cellule comme cellule de paramètres : cliquer **`...`** à droite de la cellule → **Toggle parameter cell**
4. Coller dans cette cellule :

```python
schema_name = "dev"
```

5. Dans la cellule principale, remplacer les deux lignes `saveAsTable` :

```python
# AVANT
readings_df.write.mode("overwrite").format("delta").saveAsTable("bronze_equipment_readings")
reference_df.write.mode("overwrite").format("delta").saveAsTable("ref_equipment")

# APRÈS
readings_df.write.mode("overwrite").format("delta").saveAsTable(f"{schema_name}.bronze_equipment_readings")
reference_df.write.mode("overwrite").format("delta").saveAsTable(f"{schema_name}.ref_equipment")
```

6. Exécuter le notebook et vérifier que `dev.bronze_equipment_readings` et `dev.ref_equipment` apparaissent dans le lakehouse

```python
# AVANT
health_df.write.mode("overwrite").format("delta").saveAsTable("gold_equipment_health")

health_df.write.mode("overwrite").format("delta").saveAsTable(f"{schema_name}.gold_equipment_health")
```
