# Guide : Créer le projet cobaye Microsoft Fabric pour l'atelier Git et CI/CD

## Situation d'entreprise

La société **Energia Nord**, spécialisée dans l'exploitation de parcs d'énergie renouvelable, utilise Microsoft Fabric pour centraliser les données de production de ses sites solaires et éoliens.

L'équipe Data travaille sur un workspace Fabric partagé. 

Au début, tout le monde modifiait directement les notebooks, les pipelines et les modèles dans le même espace. 

Après quelques semaines, plusieurs incidents apparaissent :

- un développeur modifie un notebook de transformation pendant qu'un autre corrige une règle métier ;
- une version fonctionnelle <u>est écrasée par erreur</u> ;
- <u>personne ne sait exactement quelle modification a cassé le calcul</u> du score de santé des équipements ;
- <u>les corrections urgentes sont faites directement</u> dans l'environnement utilisé par <u>les clients</u> ;
- les développeurs testent des changements dans le même contexte que les utilisateurs métier ;
- <u>La livraison vers la production est manuelle</u>, donc fragile et difficile à tracer.

## Decisison prise par la direction technique

La direction technique décide de mettre en place une organisation plus propre :

**Microsoft Fabric DEV -> Git / Azure Repos -> Pull Request -> Validation -> Microsoft Fabric PROD**

L'objectif est de garder Fabric comme plateforme centrale, mais d'utiliser **Git** et **Azure DevOps** pour contrôler les changements.

### 1.2 — Créer le dépôt Azure Repos

1. Dans le projet Azure DevOps, ouvrir **Repos**
2. Créer ou renommer le dépôt en **fabric-energy-ops**
3. Ne pas ajouter de README automatique pour l'instant
4. Copier l'URL HTTPS du dépôt

**URL attendue :**

`https://dev.azure.com/<organisation>/EnergiaNord-Fabric-ALM/_git/fabric-energy-ops`

> 💡 **Astuce** : Gardez cette URL dans un bloc-notes. Elle sera utilisée dans Fabric pour connecter le workspace au dépôt Git.

### 1.3 — Préparer les branches

Dans Azure Repos, créer ces branches :

| Branche                          | Rôle                                             |
| -------------------------------- | ------------------------------------------------ |
| main                             | Version stable, proche de la production          |
| develop                          | Intégration des travaux validés par l'équipe     |
| feature/health-score-v2          | Nouvelle fonctionnalité de calcul du score santé |
| bugfix/fix-temperature-threshold | Correction d'un seuil métier                     |
| hotfix/prod-alert-rule           | Correction urgente à partir de la production     |

> 💡 **Astuce** : Si vous préférez créer les branches plus tard pendant l'atelier, créez seulement main et develop maintenant. Les branches feature, bugfix et hotfix seront alors créées en démonstration.

⚠️ **Piège** : Dans un vrai projet, on évite de travailler directement sur main. Pour l'atelier, main représente la version stable livrée.

### 5.1 — Créer le notebook

**Ce que vous devez voir à l'écran** :

- Le Lakehouse lh_energy_ops attaché dans le panneau Explorer

### 5.2 — Ajouter le code d'ingestion

Dans le notebook, créer une cellule PySpark :

`from pyspark.sql.functions import col, to_timestamp readings_path = "Files/input/energy/equipment_readings.csv" reference_path = "Files/input/energy/equipment_reference.csv" readings_df = ( spark.read.option("header", True) .option("inferSchema", True) .csv(readings_path) .withColumn("ReadingTime", to_timestamp(col("ReadingTime"))) ) reference_df = ( spark.read.option("header", True) .option("inferSchema", True) .csv(reference_path) ) readings_df.write.mode("overwrite").format("delta").saveAsTable("bronze_equipment_readings") reference_df.write.mode("overwrite").format("delta").saveAsTable("ref_equipment") display(readings_df)`

### 5.3 — Exécuter le notebook

1. Cliquer **Run all**
2. Attendre la fin de l'exécution
3. Ouvrir le Lakehouse
4. Vérifier la section **Tables**

**Ce que vous devez voir à l'écran** :

- Une table bronze_equipment_readings
- Une table ref_equipment
- Les lignes CSV visibles dans l'aperçu

> 💡 **Scénario Git préparé** : ce notebook permettra de démontrer un commit simple quand un développeur ajoute une nouvelle source de fichier ou modifie un chemin d'entrée.

## Partie 6 — Créer le notebook de transformation

### 6.1 — Créer le notebook

Dans le workspace **DEV** :

1. Créer un nouveau notebook
2. Nom : **nb_02_transform_equipment_health**
3. Attacher le Lakehouse **lh_energy_ops**

### 6.2 — Ajouter le code de transformation

Créer une cellule PySpark :

`from pyspark.sql.functions import col, lit, round, when readings_df = spark.table("bronze_equipment_readings") reference_df = spark.table("ref_equipment") health_df = ( readings_df.alias("r") .join(reference_df.alias("e"), on="EquipmentId", how="left") .withColumn("LoadPct", round((col("PowerKW") / col("NominalPowerKW")) * 100, 2)) .withColumn( "TemperatureStatus", when(col("TemperatureC") >= col("CriticalTemperatureC"), lit("CRITICAL")) .when(col("TemperatureC") >= col("CriticalTemperatureC") - 10, lit("WARNING")) .otherwise(lit("NORMAL")), ) .withColumn( "VibrationStatus", when(col("VibrationMmS") >= col("CriticalVibrationMmS"), lit("CRITICAL")) .when(col("VibrationMmS") >= col("CriticalVibrationMmS") * 0.75, lit("WARNING")) .otherwise(lit("NORMAL")), ) .withColumn( "HealthStatus", when((col("TemperatureStatus") == "CRITICAL") | (col("VibrationStatus") == "CRITICAL"), lit("CRITICAL")) .when((col("TemperatureStatus") == "WARNING") | (col("VibrationStatus") == "WARNING"), lit("WARNING")) .otherwise(lit("NORMAL")), ) ) health_df.write.mode("overwrite").format("delta").saveAsTable("gold_equipment_health") display(health_df.select( "EquipmentId", "EquipmentName", "Site", "EnergyType", "PowerKW", "LoadPct", "TemperatureC", "VibrationMmS", "HealthStatus" ))`

### 6.3 — Exécuter et vérifier

1. Cliquer **Run all**
2. Ouvrir le Lakehouse
3. Vérifier la table **gold_equipment_health**

**Résultat attendu** :

- Les équipements normaux sont marqués NORMAL
- Les équipements proches d'un seuil sont marqués WARNING
- Les équipements dépassant un seuil sont marqués CRITICAL

> 💡 **Scénario Git préparé** : ce notebook sera le coeur des démonstrations. Deux développeurs pourront modifier les seuils, les colonnes ou la règle HealthStatus pour créer des branches, des merges et des conflits.

⚠️ **Piège** : Ne rendez pas la logique trop parfaite. Un petit défaut contrôlé, comme un seuil à ajuster, est utile pour démontrer une branche bugfix.

## Partie 10 — Préparer les scénarios Git de l'atelier

Cette partie ne modifie pas encore le projet. Elle définit les démonstrations que l'atelier principal pourra utiliser.

### 10.1 — Scénario 1 : commit simple

**But pédagogique** : montrer qu'un changement Fabric peut être sauvegardé dans Git.

Modification proposée :

- Ajouter une colonne ProcessingDate dans nb_02_transform_equipment_health
- Committer depuis Fabric
- Vérifier le commit dans Azure Repos

### 10.2 — Scénario 2 : branche feature

**But pédagogique** : développer une nouvelle règle sans toucher à develop.

Branche :

`feature/health-score-v2`

Modification proposée :

- Ajouter une colonne HealthScore
- Score 100 par défaut
- Retirer 40 points si température critique
- Retirer 30 points si vibration critique
- Retirer 20 points si disponibilité inférieure à 90 %

Résultat :

- Commit sur branche feature
- Pull Request vers develop
- Review du changement

### 10.3 — Scénario 3 : bugfix

**But pédagogique** : corriger une erreur métier identifiée après test.

Branche :

`bugfix/fix-temperature-threshold`

Problème simulé :

- Le seuil solaire est trop bas ou trop haut
- Certains panneaux solaires passent à tort en CRITICAL

Modification proposée :

- Ajuster la règle de température
- Ajouter une colonne RuleVersion
- Committer puis ouvrir une Pull Request

### 10.4 — Scénario 4 : conflit de versions

**But pédagogique** : montrer pourquoi Git est nécessaire dans une équipe.

Situation simulée :

- Développeur A modifie la logique HealthStatus dans feature/health-score-v2
- Développeur B modifie la même zone dans bugfix/fix-temperature-threshold
- Les deux tentent d'intégrer vers develop

Résultat :

- Azure DevOps signale un conflit dans la Pull Request ou Fabric signale un conflit au moment de la synchronisation
- L'équipe doit choisir quelle version garder ou résoudre le conflit dans Git

⚠️ **Piège pédagogique** : Préparez ce conflit volontairement dans une zone courte du notebook. Un conflit trop grand ralentit l'atelier et détourne l'attention.

### 10.5 — Scénario 5 : hotfix production

**But pédagogique** : corriger rapidement une règle critique sans attendre toutes les features en cours.

Branche :

`hotfix/prod-alert-rule`

Modification proposée :

- Changer temporairement un seuil critique
- Pull Request vers main
- Déploiement contrôlé vers PROD
- Réintégration de la correction vers develop

### 10.6 — Scénario 6 : annulation d'un commit

**But pédagogique** : montrer que Git permet de revenir proprement en arrière.

Modification proposée :

- Ajouter volontairement une colonne inutile DebugFlag
- Committer
- Montrer l'annulation avec Azure Repos ou Git
- Revenir à un état propre

> 💡 **Astuce** : Pour un public débutant, utilisez plutôt **Revert** qu'un reset destructif. Le revert garde une trace de l'annulation.

## Partie 11 — Préparer la séparation DEV / PROD

### 11.1 — Option recommandée pour l'atelier

Utiliser :

- Git integration pour le contrôle de version dans le workspace DEV ;
- Azure Repos pour les Pull Requests ;
- Fabric Deployment pipelines pour livrer de DEV vers PROD ;
- Azure DevOps pour piloter ou documenter les validations.

Flux pédagogique :

`Workspace DEV -> Commit vers develop -> Pull Request develop vers main -> Validation -> Déploiement Fabric DEV vers PROD`

### 11.2 — Créer un deployment pipeline Fabric

1. Dans Fabric, ouvrir **Deployment pipelines**
2. Cliquer **New pipeline**
3. Nom : **dp-energy-ops-dev-prod**
4. Créer deux stages :
   - **Development**
   - **Production**
5. Assigner le workspace **EN-FAB-DEV-GitCICD** au stage Development
6. Assigner le workspace **EN-FAB-PROD-GitCICD** au stage Production

**Ce que vous devez voir à l'écran** :

- Un pipeline de déploiement avec deux stages
- Le workspace DEV à gauche
- Le workspace PROD à droite

> 💡 **Pourquoi Deployment pipelines ?** Dans Fabric, ils servent à déplacer les items entre environnements en conservant une logique de cycle de vie. C'est le complément naturel de Git, qui gère l'historique et la collaboration.

### 11.3 — Premier déploiement vers PROD

1. Dans le stage Development, sélectionner les items du projet
2. Cliquer **Deploy**
3. Confirmer le déploiement vers Production
4. Ouvrir le workspace PROD
5. Vérifier que les items existent

**Ce que vous devez voir à l'écran** :

- Les notebooks existent dans PROD
- Le pipeline existe dans PROD
- Le Lakehouse existe dans PROD
- Le rapport existe dans PROD si vous l'avez créé

⚠️ **Piège** : Les données du Lakehouse ne sont pas automatiquement versionnées par Git. Selon les items et paramètres déployés, il peut être nécessaire de recharger les fichiers de test ou de configurer les dépendances dans l'environnement cible.
