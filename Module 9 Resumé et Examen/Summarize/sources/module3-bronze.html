Atelier Notebooks – Couche Bronze

ATELIER 1 : COUCHE BRONZE — INGESTION DES DONNÉES BRUTES

Lakehouse : Lakehouse_bronze
Notebook : NB_01_Bronze
Objectif : Ingérer les données brutes sans transformation (source de vérité)

🎯 Objectif de l'atelier

La couche Bronze d'une Medallion Architecture représente la fondation de votre infrastructure données. Elle reçoit les données brutes directement depuis les systèmes sources, sans aucune transformation, cleaning ou business logic. L'objectif de ce premier atelier est de charger cinq fichiers CSV provenant d'un parc de six sites de production et consommation électrique en France, en les convertissant en tables Delta persistantes au sein d'un lakehouse Microsoft Fabric.

Pourquoi cette approche ? La couche Bronze agit comme une source de vérité immutable. Elle préserve les données exactement comme elles arrivent des capteurs IoT, des systèmes SCADA et des bases de données opérationnelles, y compris avec leurs défauts (valeurs NULL, codes erreur, formats hétéroclites). Cette traçabilité est essentielle pour l'audit, le débogage et la conformité réglementaire. C'est uniquement en couche Silver que vous appliquerez des transformations métier et du nettoyage.

Au terme de cet atelier, vous aurez créé cinq tables Bronze, effectué un diagnostic de qualité initial, et identifié les anomalies qui seront traitées en aval. Vous disposerez aussi d'une base solide pour comprendre l'architecture Medallion et sa progression données brutes → données nettoyées → données métier.

📊 Contexte métier

Votre organisation gère un réseau de six sites de production et consommation d'électricité répartis en France. Deux sites industriels (capacités 5 MW et 3,5 MW), deux sites commerciaux (2 MW et 1,5 MW) et deux résidentiels (0,8 MW et 0,6 MW). Chaque site est équipé de capteurs IoT transmettant toutes les 15 minutes la consommation d'électricité pendant 30 jours. Des données complémentaires arrivent de plusieurs sources : prix spot du marché EPEX, conditions météorologiques, données de référence des sites et événements de maintenance.

Le problème : ces données brutes arrivent en formats variés (timestamps incohérents, valeurs numériques manquantes ou invalides représentées par des codes erreur comme -888 ou -999), avec des doublons et une qualité inégale selon la source. Avant d'exploiter ces données pour de l'analyse ou du machine learning, il faut d'abord les centraliser, en préserver l'intégrité, et documenter les anomalies. C'est exactement le rôle de la couche Bronze.

À l'intérieur du workspace, cliquez sur + Nouveau → Lakehouse. Nommez-le Lakehouse_bronze. Fabric crée automatiquement une structure Delta Lake avec les répertoires Tables et Files. C'est dans ce lakehouse que vous construirez votre couche Bronze.

Avant d'exécuter le notebook, vous devez placer les cinq fichiers CSV dans le répertoire Files du lakehouse. Via l'interface Fabric, accédez au lakehouse, ouvrez l'explorateur Fichiers, créez un sous-dossier data_bronze_notebooks, et uploadez les fichiers suivants :

📝 Cellule 1 : Configuration Spark et création du schéma Bronze

🔍 Avant d'exécuter

Cette cellule initialise votre environnement de travail. Vous vérifiez que la session Spark est disponible (Fabric injecte automatiquement une instance Spark pour chaque notebook), vous confirmez sa version (essentielle pour la compatibilité des API), et vous créez le schéma bronze qui servira de conteneur à toutes vos tables brutes. Un schéma dans Delta Lake est un groupement logique de tables, comparable à une base de données en SQL traditionnel. La commande CREATE SCHEMA IF NOT EXISTS garantit l'idempotence : si le schéma existe déjà, aucune erreur n'est levée.

💻 Code

<a id="verifier-que-spark-est-disponible"></a>
# Vérifier que Spark est disponible
print(f"✅ Spark version: {spark.version}")

<a id="creer-le-schema-bronze-sil-nexiste-pas-encore"></a>
# Créer le schéma bronze s'il n'existe pas encore
spark.sql("CREATE SCHEMA IF NOT EXISTS bronze")
print("✅ Schéma bronze prêt")

<a id="confirmer-le-lakehouse-actif"></a>
# Confirmer le lakehouse actif
df_schemas = spark.sql("SHOW SCHEMAS").toPandas()
print(f"✅ Schémas disponibles : {list(df_schemas.iloc[:,0])}")

✅ Schéma bronze prêt
✅ Schémas disponibles : ['bronze', 'default', 'dbo']

💡 Interprétation

Spark 3.5.x est la version stabilisée pour Fabric et supportera tous les formats Delta utilisés dans cet atelier. ✅ Le schéma bronze a été créé avec succès et apparaît dans la liste des schémas disponibles. Vous constaterez aussi la présence de schémas default et dbo, qui sont créés automatiquement par Fabric et que vous pouvez ignorer pour ce projet. 📝 Cellule 2 : Import consumption_raw.csv → Table Delta

🔍 Avant d'exécuter

Vous charger le premier fichier source, consumption_raw.csv, qui contient les données de consommation d'électricité capturées toutes les 15 minutes. PySpark offre une API spark.read.format("csv") idéale pour charger des CSV. Les options header=true et inferSchema=true instruisent Spark à traiter la première ligne comme entête et à déduire automatiquement les types de colonnes (timestamp, integer, string, etc.). Après lecture en DataFrame, vous écrivez les données au format Delta (format optimisé pour le data lakehouse) dans le schéma bronze. Le mode overwrite écrase toute table existante de même nom, garantissant un reset complet à chaque exécution.

Le comptage des lignes (count()) est une étape critique : en data engineering, on vérifie systématiquement que le nombre de lignes chargées correspond à l'attente. Une divergence majeure indiquerait un problème de lecture ou de troncature.

💻 Code

<a id="charger-le-csv-avec-pyspark"></a>
# Charger le CSV avec PySpark
df_consumption = spark.read.format("csv") \
    .option("header", "true") \
    .option("inferSchema", "true") \
    .load("Files/data_bronze_notebooks/consumption_raw.csv")

<a id="compter-les-lignes-avant-ecriture"></a>
# Compter les lignes avant écriture
nb_lignes = df_consumption.count()

<a id="creer-la-table-dans-le-schema-bronze"></a>
# Créer la table dans le schéma bronze
df_consumption.write.mode("overwrite").format("delta").saveAsTable("bronze.consumption_raw")

print(f"✅ Table bronze.consumption_raw créée : {nb_lignes} lignes")

📤 Résultat

✅ Table bronze.consumption_raw créée : 18144 lignes

💡 Interprétation

Les 18 144 lignes chargées correspondent exactement à l'attente : 6 sites × 4 mesures par heure × 24 heures × 30 jours = 17 280 lignes théoriques, plus des doublons et enregistrements de recalibrage qui expliquent le surplus. ✅ Le fichier a été lu intégralement et converti en format Delta. La table bronze.consumption_raw est maintenant accessible en SQL et persiste dans le lakehouse, formant la source de vérité pour tous les traitements aval. À noter que la couche Bronze ne connaît ni la structure ni la qualité des données ; elle les stocke telles quelles.

📝 Cellule 4 : Diagnostic qualité de consumption_raw

🔍 Avant d'exécuter

Vous effectuez à présent un diagnostic statistique de la table consumption_raw. Cette requête SQL agrégée compte plusieurs dimensions de qualité : le nombre total de lignes, le nombre de combinaisons uniques (timestamp, site_id) pour détecter les doublons, les valeurs NULL (absence totale), les valeurs négatives (codes erreur), et les outliers (consommation > 10 MW, anormalement haute). Ces métriques forment la base line qualité pour la couche Bronze et serviront de benchmark pour évaluer l'impact du nettoyage en Silver.

💻 Code

%%sql
-- Compter les NULL, codes erreur, doublons
SELECT
    COUNT(*) as total_rows,
    COUNT(DISTINCT timestamp, site_id) as unique_rows,
    COUNT(*) - COUNT(DISTINCT timestamp, site_id) as duplicates,
    SUM(CASE WHEN consumption_mw IS NULL THEN 1 ELSE 0 END) as null_values,
    SUM(CASE WHEN consumption_mw < 0 THEN 1 ELSE 0 END) as error_codes,
    SUM(CASE WHEN consumption_mw > 10 THEN 1 ELSE 0 END) as outliers
FROM bronze.consumption_raw

📤 Résultat

total_rows unique_rows duplicates null_values error_codes outliers
18144 17280 864 554 319 27

💡 Interprétation

Ce diagnostic quantifie les anomalies et guide les priorités de nettoyage. ✅ Total de 18 144 lignes, mais seulement 17 280 combinaisons uniques (timestamp, site_id), révélant 864 doublons (4,8 % des données). Typiquement, ces doublons proviennent de retransmissions suite à des timeouts réseau ou de recalibrage capteur. Ils doivent être dédupliqués en Silver, en conservant la ligne la plus récente ou la plus fiable selon le contexte métier.

554 valeurs NULL (3 %) pour consumption_mw correspondent à des défaillances capteur ou des périodes de maintenance non documentées. En Silver, vous choisirez de les filtrer ou les imputer (interpolation linéaire, valeur moyenne du site).

319 codes erreur (1,8 %) : valeurs négatives codifiant des états de panne (-888 = défaut capteur, -999 = panne réseau, -777 = calibrage en cours). Ces codes doivent être identifiés, mappés à des catégories métier, puis filtrés ou traités spécifiquement selon la logique applicative.

27 outliers (0,15 %) avec consommation > 10 MW dépassent la capacité maximale théorique de tout site (5 MW). Ces anomalies justifient une investigation : erreur d'ordre de grandeur, multiplicateur mal appliqué, ou événement métier exceptionnnel (importation externe d'électricité). À examiner en détail lors du Silver.

Ces chiffres établissent un diagnostic solide : environ 6-7 % des données présentent des anomalies identifiées. 📊 C'est un taux très raisonnable pour des données IoT brutes en production.

📝 Cellule 6 : Vérification et récapitulatif de toutes les tables

🔍 Avant d'exécuter

Vous consolidez à présent une vue d'ensemble de toutes les tables Bronze en comptant le nombre de lignes pour chacune. Cette vérification de synthèse s'assure que l'ingestion complète a réussi et qu'il n'y a pas de surprises (fichiers partiels, erreurs de lecture tardives, etc.). Une requête UNION ALL agrège les counts de cinq tables en une seule sortie de référence.

💻 Code

UNION ALL

UNION ALL
