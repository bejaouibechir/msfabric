Atelier Pipeline – Étude de cas 2

Atelier 2 : Architecture Medallion complète — Bronze → Silver → Gold avec orchestration

Contexte : Transition urbaine vers une grille énergétique intelligente

Le contexte

Une ville intelligente modernise son réseau électrique en déployant 100 capteurs IoT pour monitorer la consommation, détecter les anomalies et réduire les pertes énergétiques.

1. État des lieux

Les données brutes arrivent en continu et doivent être nettoyées, enrichies avec des seuils de référence, puis analysées pour détecter les incidents.

  • 100 capteurs IoT déployés dans 4 quartiers
  • 7200 relevés sur 3 jours (données temps réel)
  • 50 incidents détectés automatiquement
  • Données brutes non structurées nécessitant nettoyage
  • Table de référence avec seuils d'alerte par type de capteur

2. Problématique

Comment transformer les données IoT brutes (Bronze) en données nettoyées et enrichies (Silver), en détectant les anomalies, en appliquant des règles métier et en bouclant avec Until pour traiter les incidents non résolus ?

Contraintes :

  • ✅ Charger d'abord les CSV en tables Bronze
  • ✅ Enrichir avec les seuils via un Lookup (depuis table)
  • ✅ Filtrer les capteurs actifs avec If Condition
  • ✅ Boucler sur les incidents non résolus avec Until
  • ✅ Tracer les anomalies détectées

3. Solution : Pipeline de transformation intelligent

Pipeline qui :

  1. Charge les 5 CSV vers tables Bronze (sans _ ni -)
  2. Lit la table de référence avec Lookup
  3. Copie et transforme Bronze → Silver
  4. Filtre les données valides avec If Condition
  5. Boucle avec Until jusqu'à résolution des incidents
  6. Trace les traitements

Fichiers nécessaires

Téléchargez les 5 fichiers CSV fournis :

  • infrastructures_existantes.csv (100 capteurs)
  • monitoring_iot.csv (7200 relevés)
  • incidents_alertes.csv (50 incidents)
  • metriques_performance.csv (28 métriques)
  • seuils_alertes_ref.csv (4 seuils - table de référence)

Une ville intelligente déploie 100 capteurs IoT pour monitorer son réseau électrique.

Comment transformer les données brutes en données exploitables pour détecter les anomalies et réduire les pertes énergétiques ?

Questions d'analyse guidée

Question 1 : Volume de données IoT

Observez la table monitoring :

SELECT COUNT(*) as TotalReleves FROM monitoring

Résultat attendu : 7200 relevés

Interprétation :

  • 7200 relevés sur 3 jours = 2400 relevés/jour
  • 2400 relevés/jour ÷ 100 capteurs = 24 relevés/capteur/jour
  • Conclusion : Chaque capteur envoie 1 relevé par heure (24h × 3 jours = 72 relevés/capteur)

💡 Impact métier : Mesurer la fréquence de monitoring pour détecter les anomalies en temps quasi-réel.

Question 2 : Répartition géographique

Observez la table infrastructures :

SELECT Quartier, COUNT(*) as NbCapteurs 
FROM infrastructures 
GROUP BY Quartier
ORDER BY NbCapteurs DESC

Résultat obtenu :

Quartier Nb Capteurs
Quartier_Residentiel 28
Centre_Ville 26
Zone_Commerciale 23
Zone Industrielle 23

Interprétation :

  • Répartition légèrement inégale des capteurs (de 23 à 28 selon les zones)
  • Le Quartier Résidentiel est le mieux couvert (28 capteurs), cohérent avec une densité de population plus élevée
  • La Zone Industrielle et la Zone Commerciale sont moins couvertes (23 capteurs chacune), ce qui peut représenter un risque si la consommation y est plus variable ou plus élevée

💡 Impact métier : La couverture est globalement satisfaisante, mais une attention particulière devrait être portée sur la Zone Industrielle — moins couverte mais potentiellement à plus fort risque d'anomalie énergétique. Il serait pertinent d'y ajouter 2 à 5 capteurs supplémentaires pour équilibrer la surveillance.

Question 3 : État des capteurs

Observez la table infrastructures :

SELECT Statut, COUNT(*) as NbCapteurs
FROM infrastructures
GROUP BY Statut

Résultat attendu :

Statut Nb Capteurs
Actif 55
En_Maintenance 27
En_Panne 5

Interprétation :

  • 55% des capteurs sont opérationnels (55/100)
  • 27% sont en maintenance (En_Maintenance)
  • 5% sont en panne (En_Panne)
  • 13% ont un statut non renseigné (55+27+5 = 87 sur 100)

💡 Impact métier : Taux de disponibilité en dessous du seuil recommandé (< 70%). Il est urgent de planifier la remise en service des capteurs En_Maintenance et d'investiguer les capteurs En_Panne pour remonter à au moins 70% de disponibilité.

Question 4 : Criticité des incidents

Observez la table incidents :

SELECT Severite, COUNT(*) as NbIncidents
FROM incidents
GROUP BY Severite
ORDER BY 
  CASE Severite 
    WHEN 'Critique' THEN 1 
    WHEN 'Haute' THEN 2 
    WHEN 'Moyenne' THEN 3 
    WHEN 'Faible' THEN 4
  END

Résultat attendu :

Severite Nb Incidents
Critique 8
Haute 16
Moyenne 12

Analyse des résultats

Question 1 : Profil de consommation par quartier

Observez goldconsoparquartier → SQL Analytics Endpoint :

SELECT Quartier, ROUND(AVG(MoyenneConso_kWh), 2) AS ConsoMoyenne
FROM goldconsoparquartier
GROUP BY Quartier
ORDER BY ConsoMoyenne DESC

Interprétation : Le quartier avec la plus forte consommation moyenne révèle les zones prioritaires pour l'optimisation énergétique.

Question 2 : Incidents les plus critiques

Observez goldincidents :

SELECT TypeIncident, Severite, NbIncidents, TempsResolutionMoyen_Min
FROM goldincidents
WHERE Severite = 'Critique'
ORDER BY NbIncidents DESC

Interprétation : Les incidents critiques les plus fréquents orientent les investissements en maintenance préventive.

Question 3 : KPI de disponibilité réseau

Observez goldmetriques :

SELECT Quartier,
       ROUND(AVG(Taux_Disponibilite_Pct), 2) AS DisponibiliteMoyenne,
       ROUND(AVG(Pertes_Energie_Pct), 2)     AS PertesMoyennes
FROM goldmetriques
GROUP BY Quartier
ORDER BY DisponibiliteMoyenne ASC

Interprétation : Le quartier avec la plus faible disponibilité est la priorité d'intervention. Un taux < 95% est considéré comme critique dans une grille intelligente.
