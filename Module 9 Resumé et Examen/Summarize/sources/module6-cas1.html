Eventstream – Traitement des Données Réelles

Atelier : Monitoring temps réel d'un parc éolien — Eventstream & KQL Database

Vous allez ingérer des données IoT simulées (capteurs de turbines éoliennes) dans Microsoft Fabric via Eventstream, les stocker dans une KQL Database, les transformer en temps réel, les analyser avec des requêtes KQL, les visualiser dans un Real-Time Dashboard, accélérer le dashboard avec une Materialized View et configurer des alertes automatiques avec Activator.

Résultat attendu : un pipeline temps réel complet qui supervise 5 turbines éoliennes, met en évidence les anomalies (surchauffe, vibrations, sous-performance), enrichit les événements dans le flux et expose un tableau de bord utilisable en conditions quasi réelles.

⚠️ Note pédagogique sur l'ordre des étapes : L'atelier démarre le simulateur Python avant de configurer la destination Eventhouse. Ce choix est intentionnel — Fabric a besoin de données réelles qui circulent pour valider le schéma JSON dans le wizard de configuration. Si vous configurez la destination sans données, le bouton Finish reste grisé.

Fichiers nécessaires

Créer le script

Créer un fichier wind_turbine_simulator.py et coller ce code :

import json
import time
import random
from datetime import datetime, timezone
from azure.eventhub import EventHubProducerClient, EventData

<a id="section"></a>
# ============================================================
<a id="configuration-coller-vos-valeurs-depuis-leventstream"></a>
# CONFIGURATION — Coller vos valeurs depuis l'Eventstream
<a id="section-1"></a>
# ============================================================
CONNECTION_STR = "<votre_connection_string_primary_key>"
EVENTHUB_NAME = "<votre_event_hub_name>"
<a id="section-2"></a>
# ============================================================

TURBINES = ["WT-001", "WT-002", "WT-003", "WT-004", "WT-005"]
PARK_NAME = "Parc Eolien Bizerte"

def generate_turbine_event(turbine_id):
    wind_speed = random.uniform(3.0, 25.0)

    # Courbe de puissance simplifiee
    if wind_speed < 3.5:
        power = 0
    elif wind_speed > 22:
        power = 0
    else:
        power = min(3000, (wind_speed - 3.5) ** 2 * 18)

    rotor_rpm = wind_speed * 1.2 + random.uniform(-1, 1)
    gen_temp = 55 + (power / 3000) * 35 + random.uniform(-3, 3)
    vibration = 2.0 + random.uniform(0, 1.5)

    # Injection d'anomalies (10% du temps)
    # Option atelier intensif :
    # Pour observer plus vite les anomalies pendant une demo courte,
    # vous pouvez temporairement remplacer 0.10 par 0.25 ou 0.30.
    # Revenez ensuite a 0.10 pour garder un flux plus realiste.
    if random.random() < 0.10:
        anomaly_type = random.choice(["overheat", "vibration", "underperform"])
        if anomaly_type == "overheat":
            gen_temp += random.uniform(25, 45)
        elif anomaly_type == "vibration":
            vibration += random.uniform(5, 12)
        elif anomaly_type == "underperform":
            power *= random.uniform(0.2, 0.5)

    return {
        "TurbineId": turbine_id,
        "Timestamp": datetime.now(timezone.utc).isoformat(),
        "WindSpeedMs": round(wind_speed, 2),
        "RotorRPM": round(rotor_rpm, 2),
        "PowerOutputKW": round(power, 2),
        "GeneratorTempC": round(gen_temp, 2),
        "VibrationMmS": round(vibration, 2),
        "NacelleOrientation": round(random.uniform(0, 360), 1),
        "AmbientTempC": round(random.uniform(15, 35), 1),
        "ParkName": PARK_NAME
    }

def main():
    producer = EventHubProducerClient.from_connection_string(
        conn_str=CONNECTION_STR,
        eventhub_name=EVENTHUB_NAME
    )
    print("Envoi d'evenements vers Fabric Eventstream...")

    try:
        while True:
            batch = producer.create_batch()
            for turbine_id in TURBINES:
                event = generate_turbine_event(turbine_id)
                batch.add(EventData(json.dumps(event)))
                print(f"  [{event['Timestamp'][:19]}] {turbine_id} | "
                      f"Vent: {event['WindSpeedMs']}m/s | "
                      f"Puissance: {event['PowerOutputKW']}kW | "
                      f"Temp: {event['GeneratorTempC']}C | "
                      f"Vibration: {event['VibrationMmS']}mm/s")
            producer.send_batch(batch)
            print(f"  -> Batch de {len(TURBINES)} evenements envoye\n")
            time.sleep(5)
    except KeyboardInterrupt:
        print("Arret du simulateur.")
    finally:
        producer.close()

if __name__ == "__main__":
    main()

2.4 — Ajouter la destination Eventhouse

💡 Pourquoi Direct ingestion ? Le formulaire "Event processing before ingestion" de Fabric présente un bug d'interface qui rend le bouton Save systématiquement inaccessible, quelle que soit la manipulation tentée. Nous utilisons donc Direct ingestion comme chemin principal — c'est une approche officiellement documentée par Microsoft, et la configuration de la table se fait ensuite dans un wizard séparé qui fonctionne parfaitement dès lors que le simulateur envoie déjà des données.

4.1 — Vérification rapide

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| take 20

  • extend : Crée une nouvelle colonne EventTime en convertissant Timestamp (texte → date/heure).

  • take 20 : Renvoie 20 lignes arbitraires pour un aperçu immédiat.

Ce que vous voyez : les derniers événements ingérés, avec les colonnes de télémétrie brutes et éventuellement les colonnes enrichies.

4.2 — Production moyenne par turbine (10 dernières minutes)

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(10m)
| summarize
    AvgPower = avg(PowerOutputKW),
    AvgWind = avg(WindSpeedMs),
    EventCount = count()
  by TurbineId
| order by AvgPower desc

  • where EventTime > ago(10m) : Filtre les 10 dernières minutes.

  • summarize ... by TurbineId : Groupe par turbine et calcule moyenne/occurrences.

  • order by AvgPower desc : Classe de la plus productive à la moins productive.

Ce que vous voyez : chaque turbine avec sa puissance moyenne, sa vitesse de vent moyenne et son nombre d'événements récents.

4.3 — Détection d'anomalies thermiques (> 95°C)

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where GeneratorTempC > 95
| project EventTime, TurbineId, GeneratorTempC, PowerOutputKW, WindSpeedMs
| order by GeneratorTempC desc

  • where GeneratorTempC > 95 : Seuil critique au-delà du risque de casse.

  • project : Ne conserve que les colonnes utiles pour le diagnostic.

  • order by GeneratorTempC desc : Les plus chaudes d'abord.

Ce que vous voyez : uniquement les événements où le générateur a dépassé 95°C.

4.4 — Détection de vibrations anormales (> 8 mm/s)

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where VibrationMmS > 8.0
| project EventTime, TurbineId, VibrationMmS, RotorRPM, GeneratorTempC
| order by VibrationMmS desc

  • where VibrationMmS > 8.0 : Seuil de vibration dangereuse.

  • Idem 4.3, mais appliqué aux vibrations.

Ce que vous voyez : les événements avec des vibrations dangereuses.

4.5 — Rendement énergétique par turbine (fenêtre de 5 min)

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where WindSpeedMs between (4.0 .. 20.0)
| summarize
    AvgPower = avg(PowerOutputKW),
    AvgWind = avg(WindSpeedMs)
  by TurbineId, bin(EventTime, 5m)
| extend EfficiencyRatio = AvgPower / (AvgWind * AvgWind * AvgWind) * 1000
| order by EventTime desc, TurbineId

  • bin(EventTime, 5m) : Regroupe les événements par tranches de 5 minutes.

  • extend EfficiencyRatio = ... / (AvgWind³) * 1000 : Rendement simplifié (puissance / vent³).

  • Utile pour comparer l'efficacité entre turbines à vent égal.

Ce que vous voyez : un ratio de rendement simplifié par turbine toutes les 5 minutes.

4.6 — État de santé global des turbines

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| summarize
    AvgTemp = avg(GeneratorTempC),
    MaxTemp = max(GeneratorTempC),
    AvgVibration = avg(VibrationMmS),
    MaxVibration = max(VibrationMmS),
    AvgPower = avg(PowerOutputKW),
    TotalEvents = count()
  by TurbineId
| extend HealthStatus = case(
    MaxTemp > 95 or MaxVibration > 8.0, "CRITIQUE",
    MaxTemp > 85 or MaxVibration > 6.0, "ATTENTION",
    "NORMAL")
| order by HealthStatus asc, TurbineId asc

  • case(...) : Attribue un statut CRITIQUE / ATTENTION / NORMAL.

  • Synthèse par turbine sur température max, vibration max, puissance moyenne.

  • order by HealthStatus asc : Remonte d'abord les plus critiques.

Ce que vous voyez : un tableau de synthèse avec un statut CRITIQUE, ATTENTION ou NORMAL par turbine.

4.7 — Courbe glissante de température (granularité 1 minute)

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(1h)
| summarize AvgTemp = avg(GeneratorTempC) by TurbineId, bin(EventTime, 1m)
| order by EventTime asc

  • bin(EventTime, 1m) : Agrège par minute.

  • Idéal pour un graphique en ligne où on suit l'évolution minute par minute.

Ce que vous voyez : une série temporelle idéale pour un graphique en ligne.

4.8 — Détection de sous-performance par comparaison puissance/vent

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(30m)
| where WindSpeedMs between (6.0 .. 20.0)
| extend ExpectedPowerKW = min_of(3000.0, pow(WindSpeedMs - 3.5, 2) * 18.0)
| extend PerformanceRatio = iif(ExpectedPowerKW == 0, real(null), PowerOutputKW / ExpectedPowerKW)
| where PerformanceRatio < 0.60
| project EventTime, TurbineId, WindSpeedMs, PowerOutputKW, ExpectedPowerKW, PerformanceRatio
| order by PerformanceRatio asc

  • pow(WindSpeedMs - 3.5, 2) * 18.0 : Puissance théorique attendue.

  • PerformanceRatio < 0.60 : La turbine produit moins de 60% de l'attendu → sous-performance.

Ce que vous voyez : les cas où la puissance réellement produite est très en dessous de la puissance attendue.

4.9 — Carte de chaleur simple de la température

TurbineEvents
| extend EventTime = todatetime(Timestamp)
| where EventTime > ago(1h)
| summarize AvgTemp = avg(GeneratorTempC) by TurbineId, TimeSlot = bin(EventTime, 5m)
| order by TimeSlot asc, TurbineId asc

  • summarize AvgTemp by TurbineId, bin(EventTime, 5m) : Préparé pour heatmap.

  • Chaque case = température moyenne d'une turbine sur 5 minutes.

Ce que vous voyez : un tableau prêt à être affiché en heatmap dans un dashboard.

4.12 — Tendance récente de production par comparaison entre deux fenêtres

let CurrentWindow =
    TurbineEvents
    | extend EventTime = todatetime(Timestamp)
    | where EventTime between (ago(10m) .. now())
    | summarize CurrentAvgPower = avg(PowerOutputKW) by TurbineId;
let PreviousWindow =
    TurbineEvents
    | extend EventTime = todatetime(Timestamp)
    | where EventTime between (ago(20m) .. ago(10m))
    | summarize PreviousAvgPower = avg(PowerOutputKW) by TurbineId;
CurrentWindow
| join kind=inner PreviousWindow on TurbineId
| extend DeltaPower = CurrentAvgPower - PreviousAvgPower
| extend Trend = case(DeltaPower > 150, "HAUSSE", DeltaPower < -150, "BAISSE", "STABLE")

| order by DeltaPower asc

Partie 6 — Pipeline d'alertes industriel : Update Policy + Function + Materialized View

Dans cette partie, vous allez construire un système d'alerting complet entièrement dans l'Eventhouse, sans dépendance externe. L'architecture finale est :

TurbineEvents → (Update Policy) → fn_DetectAnomaly() → TurbineAlerts → (Materialized View) → MV_AlertSummary → (Dashboard)

💡 Pourquoi cette approche ? L'Update Policy est un mécanisme natif de l'Eventhouse : à chaque ingestion dans TurbineEvents, la fonction de détection s'exécute automatiquement et écrit les anomalies dans TurbineAlerts. Pas d'email, pas de Teams, pas de dépendance externe. Les alertes sont immédiatement requêtables et visualisables dans le dashboard.

6.1 — Créer la table TurbineAlerts

  1. Ouvrir WindFarmEventhouse_queryset
  2. Coller et exécuter cette commande :
.create table TurbineAlerts (
    AlertTime: datetime,
    TurbineId: string,
    AlertType: string,
    Severity: string,
    AlertValue: real,
    Threshold: real,
    Message: string
)
  1. Cliquer Run

Ce que vous devez voir : un message de succès. La table TurbineAlerts apparaît dans le panneau gauche sous Tables.

6.2 — Créer la fonction de détection fn_DetectAnomaly

La logique de détection des 3 types d'anomalies est centralisée dans une seule fonction réutilisable. L'Update Policy appellera cette fonction — si vous souhaitez ajouter une règle, vous modifiez uniquement la fonction.

  1. Coller et exécuter cette commande :
.create-or-alter function fn_DetectAnomaly() {
    TurbineEvents
    | extend EventTime = todatetime(Timestamp)
    | extend ExpectedPowerKW = min_of(3000.0, pow(WindSpeedMs - 3.5, 2) * 18.0)
    | extend PerformanceRatio = iif(
        ExpectedPowerKW == 0 or WindSpeedMs < 6.0 or WindSpeedMs > 20.0,
        real(null),
        PowerOutputKW / ExpectedPowerKW)
    | where GeneratorTempC > 95
        or VibrationMmS > 8
        or (isnotnull(PerformanceRatio) and PerformanceRatio < 0.60)
    | extend AlertType = case(
        GeneratorTempC > 95, "SURCHAUFFE",
        VibrationMmS > 8,    "VIBRATION",
                             "SOUS_PERFORMANCE")
    | extend AlertValue = case(
        GeneratorTempC > 95, GeneratorTempC,
        VibrationMmS > 8,    VibrationMmS,
                             round(PerformanceRatio * 100, 1))
    | extend Threshold = case(
        GeneratorTempC > 95, 95.0,
        VibrationMmS > 8,    8.0,
                             60.0)
    | extend Severity = case(
        GeneratorTempC > 120 or VibrationMmS > 14, "CRITIQUE",
                                                    "ATTENTION")
    | extend Message = strcat(
        AlertType, " sur ", TurbineId,
        " — Valeur: ", tostring(round(AlertValue, 2)),
        " / Seuil: ", tostring(Threshold))
    | project AlertTime = EventTime, TurbineId, AlertType, Severity, AlertValue, Threshold, Message
}
  1. Cliquer Run

Ce que vous devez voir : un message de succès. La fonction fn_DetectAnomaly apparaît sous Functions dans le panneau gauche.

💡 Astuce : Testez la fonction seule avant de l'attacher à la policy — exécutez fn_DetectAnomaly() dans le queryset et vérifiez que des lignes d'anomalies apparaissent.

6.3 — Activer l'Update Policy

  1. Coller et exécuter cette commande :
.alter table TurbineAlerts policy update
@'[{"IsEnabled": true, "Source": "TurbineEvents", "Query": "fn_DetectAnomaly()", "IsTransactional": false, "PropagateIngestionProperties": false}]'
  1. Cliquer Run

💡 Ce qui se passe maintenant : à chaque batch ingéré dans TurbineEvents, Fabric exécute automatiquement fn_DetectAnomaly() et écrit les anomalies dans TurbineAlerts. Le pipeline est actif en temps réel.

Partie 7 — Materialized View sur TurbineEvents

💡 Rappel : Une MV_AlertSummary sur TurbineAlerts a déjà été créée en Partie 6.4. Cette partie crée une seconde Materialized View, mv_turbine_health_1m, sur la table brute TurbineEvents. Les deux vues ont des rôles distincts : MV_AlertSummary agrège les alertes, mv_turbine_health_1m agrège la télémétrie brute pour accélérer les tuiles du dashboard opérationnel.

Dans un contexte réel, les dashboards exécutent souvent les mêmes agrégations en permanence. Une Materialized View pré-calcule les résultats une fois et les met à jour incrémentalement.

backfill=true recalcule immédiatement toutes les données historiques. Les cinq agrégats (puissance, température, vibration, vent, count) sont pré-calculés par turbine et par minute.

  1. La table TurbineAlerts reçoit de nouvelles lignes à chaque cycle du simulateur
  2. Les trois types d'alertes sont présents : SURCHAUFFE, VIBRATION, SOUS_PERFORMANCE
  3. Les sévérités CRITIQUE et ATTENTION sont correctement attribuées
  4. MV_AlertSummary reflète les comptages agrégés par heure
  5. Le panneau Monitoring → Ingestion de l'Eventhouse ne montre aucune erreur d'Update Policy

💡 Astuce : Pendant une démonstration, gardez trois onglets ouverts : simulateur Python, dashboard, KQL queryset. C'est la combinaison la plus parlante pour montrer le temps réel.

Partie 9 — Monitoring du Workspace

Le Workspace Monitoring de Microsoft Fabric est un Eventhouse dédié qui collecte automatiquement les logs d'activité de votre workspace : ingestion, requêtes, commandes DDL, performances. Il vous permet de diagnostiquer les erreurs d'Update Policy, les goulets d'ingestion et les requêtes lentes directement en KQL.

⚠️ Prérequis : Vous devez avoir le rôle Admin sur le workspace pour activer cette fonctionnalité.

9.1 — Activer le Workspace Monitoring

Chemin principal — Workspace Settings :

  1. Dans votre workspace, cliquer sur l'icône engrenage ⚙️ en haut à droite → Workspace settings
  2. Dans le panneau gauche, cliquer Monitoring
  3. Cliquer le bouton + Eventhouse
  4. Attendre quelques secondes

Ce que vous voyez à l'écran :

  • Message de confirmation : "Successfully added the monitoring Eventhouse and turned on logging"
  • Log workspace activity : On
  • Un lien cliquable Monitoring database apparaît dans ce même panneau

💡 Accès alternatif : depuis l'item WindFarmEventhouse dans le workspace, dans le panneau de navigation gauche, un lien Monitoring permet d'accéder directement à la base de monitoring.

9.2 — Accéder à la base Monitoring

Option A — Via le lien dans Workspace Settings :

  1. Rester dans Workspace settings → Monitoring
  2. Cliquer le lien Monitoring database

Option B — Via l'Eventhouse :

  1. Depuis le workspace, ouvrir WindFarmEventhouse
  2. Dans le panneau gauche, cliquer Monitoring

Dans les deux cas, vous atterrissez dans une KQL Database dédiée, distincte de WindFarmDB.

9.3 — Découvrir les tables disponibles

Avant d'écrire des requêtes, explorez les tables présentes dans la base Monitoring :

.show tables
