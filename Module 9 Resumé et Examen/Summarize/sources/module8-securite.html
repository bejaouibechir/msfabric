Atelier sécurité Microsoft Fabric

Couche 1 — RBAC Workspace

Étape 1 — Attribuer le rôle Workspace Viewer au compte participant

Objectif : Attribuer le rôle Viewer au compte participant et comprendre l’impact de ce rôle sur la sécurité globale.

Pourquoi :
Le rôle Workspace Viewer est le seul rôle qui n’autorise aucune modification ni exécution dangereuse. Il constitue le plafond de sécurité pour tous les utilisateurs finaux. Les rôles Admin et Member contournent automatiquement la RLS, l’OLS et la plupart des restrictions item-level. C’est pourquoi il faut toujours partir du rôle Viewer avant d’appliquer des sécurités plus fines.

Actions formateur (compte dev – Workspace Admin) :

  1. Ouvrez le workspace FinCorp_Initial.

  2. En haut à droite, cliquez sur le bouton Manage access.

  3. Cliquez sur + Add user or group.

  4. Dans la zone de recherche, tapez le nom du compte participant et sélectionnez-le.

  5. Dans la liste déroulante des rôles, choisissez Viewer.

  6. Cliquez sur le bouton Add.

Actions participant :

  1. Connectez-vous à Microsoft Fabric avec le compte participant.

  2. Ouvrez le workspace FinCorp_Initial.

Ce que vous devez voir :

  • Le participant voit tous les items du workspace (Lakehouse, SQL endpoint, Rapport, Modèle sémantique).

  • Aucun bouton Edit, Delete, New ou Manage n’est disponible.

  • Le participant peut uniquement ouvrir les rapports et visualiser les données selon les permissions héritées.

Couche 2 — Sécurité d’accès aux objets Fabric (item-level permissions)

Étape 1 — Observer le baseline (permissions héritées)

Objectif : Visualiser les permissions héritées du rôle Viewer sur chaque item avant toute modification.

Pourquoi :
Avant de restreindre quoi que ce soit, il faut savoir ce que le rôle Viewer hérite automatiquement. Cela permet de comprendre précisément quels droits sont dangereux et doivent être retirés. Le Viewer hérite par défaut de permissions minimales, mais certaines restent trop permissives.

Actions formateur (compte dev – Workspace Admin) :

  1. Restez connecté avec le compte dev dans le workspace FinCorp_Initial.

  2. Pour chaque item suivant, cliquez sur les … (More options) à droite du nom de l’item, puis choisissez Manage permissions :

  • Lakehouse principal

  • SQL analytics endpoint

  • Rapport Power BI

  • Modèle sémantique SM_SalesFinCorp

Actions participant :

  1. Connectez-vous avec le compte participant.

  2. Ouvrez chaque item un par un et notez ce que vous pouvez faire (ouvrir, éditer, exécuter, etc.).

Ce que vous devez voir :

  • Lakehouse : Read, ViewOutput

  • SQL analytics endpoint : Read, ReadData, ReadAll

  • Rapport Power BI : Read, Write

  • Modèle sémantique : Read

Étape 2 — Retirer ReadAll du Lakehouse

Objectif : Supprimer la permission ReadAll sur l’item Lakehouse pour bloquer l’accès à l’exploration des fichiers bruts et des tables dans l’interface Lakehouse.

Pourquoi :
La permission ReadAll (Read all with Apache Spark) permet d’accéder directement aux fichiers et aux tables via l’explorateur Lakehouse (onglet Files et Tables). Sans cette permission, le participant ne peut plus visualiser ni prévisualiser les données brutes, même s’il conserve la permission Read héritée du rôle Workspace Viewer. Cela renforce la sécurité tout en gardant ReadData sur le SQL analytics endpoint pour le rapport DirectLake.

Actions formateur (compte dev – Workspace Admin) :

  1. Restez connecté avec le compte dev dans le workspace FinCorp_Initial.

  2. Localisez l’item Lakehouse (LH_FinCorp).

  3. Cliquez sur les … (More options) à droite du Lakehouse.

  4. Choisissez Manage permissions.

  5. Dans la ligne du compte participant, cliquez sur les … à droite de ses permissions.

  6. Choisissez Remove ReadAll.

  7. Confirmez la suppression.

Actions participant :

  1. Connectez-vous avec le compte participant.

  2. Ouvrez le workspace FinCorp_Initial.

  3. Cliquez sur l’item Lakehouse (LH_FinCorp).

Ce que vous devez voir :

  • Les sections Tables et Files dans l’Explorer du Lakehouse affichent des croix rouges ou sont inaccessibles.

  • Le message « Some features are not available because of your permissions » apparaît en haut de la page.

  • Le participant ne peut plus voir ni prévisualiser les fichiers bruts ni explorer librement les tables.

Étape 3 — Retirer Reshare du rapport Power BI

Objectif : Supprimer la permission qui permet la modification du rapport pour que le participant ne puisse que le consulter.

Pourquoi :
Le rôle Workspace Viewer hérite souvent de la permission Reshare ou Write sur les rapports. Cela permet d’ouvrir le rapport en mode édition. Nous voulons limiter le participant à la consultation seule. Dans l’interface actuelle, la permission dangereuse visible est Reshare. Nous allons la retirer.

Actions formateur (compte dev – Workspace Admin) :

  1. Restez connecté avec le compte dev dans le workspace FinCorp_Initial.

  2. Localisez le rapport Power BI.

  3. Cliquez sur les … (More options) à droite du nom du rapport.

  4. Choisissez Manage permissions.

  5. Dans la ligne du compte participant, cliquez sur les … à droite de ses permissions.

  6. Choisissez Remove reshare.

  7. Confirmez la suppression.

Actions participant :

  1. Connectez-vous avec le compte participant.

  2. Ouvrez le workspace FinCorp_Initial.

  3. Localisez et ouvrez le rapport Power BI.

Ce que vous devez voir :

  • Le bouton Edit n’est plus disponible sur le rapport.

  • Le rapport s’ouvre uniquement en mode consultation.

  • Le participant peut visualiser les visuels et appliquer des filtres, mais ne peut ni modifier le rapport, ni ajouter des pages, ni sauvegarder des changements.

Étape 4 — Vérifier les permissions du modèle sémantique

Objectif : Vérifier que le modèle sémantique SM_SalesFinCorp est visible et accessible en lecture seule pour le compte participant.

Pourquoi :
Le modèle sémantique doit rester visible pour le participant afin qu’il puisse consommer les données via le rapport. Cependant, il ne doit pas disposer des permissions Build, Write ou Reshare, qui permettraient de créer de nouveaux rapports ou de modifier le modèle. Le fait que le modèle ne soit pas visible pour le participant indique un problème de permission plus large que nous devons corriger ou expliquer.

Actions formateur (compte dev – Workspace Admin) :

  1. Restez connecté avec le compte dev dans le workspace FinCorp_Initial.

  2. Localisez le modèle sémantique SM_SalesFinCorp.

  3. Cliquez sur les … (More options) à droite du modèle.

  4. Choisissez Manage permissions.

  5. Dans la ligne du compte participant, vérifiez les permissions actuelles.

  6. Assurez-vous que la permission Read est bien présente via l’héritage du rôle Workspace Viewer.

Actions participant :

  1. Connectez-vous avec le compte participant.

  2. Ouvrez le workspace FinCorp_Initial.

  3. Vérifiez si le modèle sémantique SM_SalesFinCorp apparaît dans la liste des items.

Ce que vous devez voir :

  • Avec le compte dev : le modèle sémantique est visible et les permissions du participant sont limitées à Read.

  • Avec le compte participant : le modèle sémantique doit apparaître dans le workspace, même s’il ne peut pas l’éditer.

Étape 5 — Vérifier et retirer Build du modèle sémantique

Objectif : S’assurer que le compte participant ne possède pas la permission Build sur le modèle sémantique SM_SalesFinCorp, afin d’empêcher la création de nouveaux rapports ou l’extraction indirecte des données.

Pourquoi :
La permission Build permet de créer de nouveaux rapports à partir du dataset, de connecter Excel au modèle, d’interroger le modèle via outils externes. Dans un scénario gouverné entreprise, un Business Analyst Viewer ne doit pas disposer de Build par défaut. On conserve uniquement Read.

Actions formateur (compte dev — Workspace Admin) :

  1. Ouvrir le workspace FinCorp_Initial

  2. Localiser SM_SalesFinCorp

  3. Cliquer sur …

  4. Choisir Manage permissions

  5. Repérer la ligne du compte participant

  6. Vérifier si Build est présent

  7. Si présent : cliquer sur Remove Build

  8. Confirmer la suppression

Actions participant :

  1. Se connecter avec le compte participant

  2. Ouvrir le workspace FinCorp_Initial

  3. Essayer :
    New report → From semantic model

Ce que vous devez voir :

  • Le modèle reste visible.

  • Le rapport existant fonctionne.

  • La création d’un nouveau rapport est impossible.

Couche 3 — Sécurité du modèle sémantique (RLS / CLS)

Étape 1 — Implémenter Row-Level Security (RLS)

Objectif : Restreindre l’accès aux lignes du dataset afin que le participant ne voie que les données autorisées selon son périmètre métier.

Pourquoi :
La Row-Level Security permet de filtrer dynamiquement les lignes visibles dans le modèle sémantique selon l’utilisateur connecté. Elle constitue le mécanisme principal de sécurisation des données analytiques dans un environnement Fabric gouverné. Sans RLS, un utilisateur Viewer peut visualiser toutes les lignes accessibles via le dataset.

Actions formateur (compte dev – Workspace Admin) :

  1. Ouvrez le modèle sémantique SM_SalesFinCorp.

  2. Cliquez sur Security.

  3. Cliquez sur + New role.

  4. Nommer le rôle : SalesRegion_Filter.

  5. Sélectionnez la table contenant la colonne Region.

  6. Ajouter la règle :

Region = USERPRINCIPALNAME()

  1. Enregistrer la règle.

  2. Ajouter le compte participant au rôle SalesRegion_Filter.

  3. Sauvez la configuration.

Actions participant :

  1. Connectez-vous avec le compte participant.

  2. Ouvrez le rapport Power BI lié au dataset SM_SalesFinCorp.

Ce que vous devez voir :

  • Le participant ne voit que les lignes correspondant à son périmètre.

  • Les autres régions disparaissent des visuels.

  • Les agrégations du rapport se recalculent automatiquement selon le filtre appliqué.

Étape 2 — Vérifier l’application effective de la RLS

Objectif : Confirmer que la règle RLS s’applique réellement au participant dans le rapport.

Pourquoi :
Configurer une RLS ne garantit pas son application immédiate. Il est nécessaire de vérifier que le rôle est bien assigné et que le filtrage fonctionne côté utilisateur final.

Actions formateur (compte dev – Workspace Admin) :

  1. Retournez dans Security du modèle SM_SalesFinCorp.

  2. Vérifiez que le compte participant apparaît dans le rôle SalesRegion_Filter.

  3. Cliquez sur View as role.

  4. Sélectionnez SalesRegion_Filter.

  5. Vérifiez les données visibles en simulation.

Actions participant :

  1. Rafraîchissez le rapport.

  2. Naviguez entre les pages du rapport.

  3. Comparez les valeurs visibles avec celles attendues.

Ce que vous devez voir :

  • Les visuels affichent uniquement les données autorisées.

  • Aucune ligne hors périmètre n’est visible.

  • Les totaux globaux changent par rapport à la vue Admin.

Étape 3 — Implémenter Column-Level Security (CLS)

Objectif : Masquer certaines colonnes sensibles du modèle sémantique pour empêcher leur consultation par le participant.

Pourquoi :
La Column-Level Security protège les colonnes contenant des informations sensibles comme salaires, marges ou emails clients. Même si l’utilisateur a accès aux lignes via RLS, ces colonnes restent invisibles.

  2. Passez en Model view.

  3. Sélectionnez la colonne Salary.

  4. Ouvrez Properties.

  5. Activez le masquage de la colonne.

  6. Répétez pour :

  • Margin

  • CustomerEmail

  1. Enregistrez les modifications.

Actions participant :

  1. Connectez-vous avec le compte participant.

  2. Ouvrez le rapport Power BI.

  3. Vérifiez les champs disponibles dans les visuels.

Ce que vous devez voir :

  • Les colonnes Salary, Margin et CustomerEmail n’apparaissent plus.

  • Elles ne sont pas disponibles dans les filtres.

  • Elles ne sont pas visibles dans les champs du rapport.

Étape 4 — Vérifier l’application effective de la CLS

Objectif : Confirmer que les colonnes sensibles sont réellement invisibles pour le participant.

Pourquoi :
Certaines colonnes peuvent rester visibles via cache ou session active. Une vérification côté utilisateur garantit que la CLS est correctement appliquée.

Actions formateur (compte dev – Workspace Admin) :

  2. Publiez à nouveau le modèle si nécessaire.

  3. Parcourez les champs disponibles.

Ce que vous devez voir :

  • Les colonnes sensibles restent invisibles.

  • Aucun champ correspondant n’apparaît dans le dataset côté participant.

Couche 4 — Row-Level Security (RLS)

Étape préalable — Configurer une Fixed Identity sur le modèle sémantique

Objectif : Passer le modèle de SSO à Fixed Identity pour débloquer Manage roles.

Pourquoi : En mode SSO par défaut, Manage roles est grisé — Fabric ne peut pas appliquer le RLS sans une identité fixe pour accéder aux données.

Actions formateur (compte dev – Workspace Admin) :

  1. Dans FinCorp_Initial, cliquer sur ... → Settings sur SM_SalesFinCorp
  2. Dérouler la section Gateway and cloud connections
  3. Dans le dropdown Maps to, sélectionner Create a connection
  4. Remplir le formulaire :
    - Connection name : devconnection
    - Authentication method : OAuth 2.0
    - Cliquer Edit credentials → se connecter avec le compte dev
    - Single sign-on : laisser décoché
  5. Cliquer Create
  6. Dans le dropdown Maps to, sélectionner devconnection
  7. Cliquer Apply

Ce que vous devez voir : Le dropdown affiche devconnection au lieu de Default: Single Sign-On.
