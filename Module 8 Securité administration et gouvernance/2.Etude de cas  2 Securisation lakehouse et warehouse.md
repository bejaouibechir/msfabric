# Atelier : Sécurisation Microsoft Fabric - rôles Workspace, permissions d'item, limites Lakehouse et implémentation complète avec Warehouse

Vous allez construire un atelier de sécurité **Microsoft Fabric** en deux temps :

1. une **mise en contexte Lakehouse**, uniquement pour montrer :
  
  - les rôles **Admin / Member / Contributor / Viewer**
  - l'impact des permissions d'item via **Manage permissions**
  - les limites du **Lakehouse** pour les démonstrations **T-SQL** granulaires
2. un **mise en contexte Warehouse**, qui reprend la logique fonctionnelle de sécurisation mais avec un moteur plus adapté aux démonstrations SQL avancées :
  
  - schémas `bronze`, `silver`, `gold`, `security`
  - permissions SQL fines
  - **RLS**
  - **CLS**
  - **OLS**
  - tests utilisateurs reproductibles

Les comptes pédagogiques utilisés dans l'atelier sont :

- `participant@contactemeraudeit.onmicrosoft.com` : utilisateur métier restreint
- `test@contactemeraudeit.onmicrosoft.com` : second utilisateur de test

Le compte `dev@contactemeraudeit.onmicrosoft.com` n'est mentionné que comme **compte d'administration du formateur** pour exécuter les manipulations qui exigent un niveau de droit élevé.

Résultat attendu : à la fin de l'atelier, les apprenants comprennent :

- pourquoi les rôles de workspace ne suffisent pas à eux seuls
- comment appliquer des permissions d'item dans Fabric
- pourquoi le **Lakehouse** montre des limites pratiques pour certains scénarios **T-SQL**
- pourquoi le **Warehouse** est plus pertinent pour une démonstration complète de sécurité SQL dans Fabric

### 1.6 - Présenter brièvement les permissions d'item

Quand vous ouvrez **Manage permissions**, Fabric peut exposer plusieurs droits fins selon le type d'item et l'état de votre tenant. Il n'est pas nécessaire d'entrer trop tôt dans tous les détails, mais il est très utile d'en donner une lecture simple.

| Permission | Explication pédagogique simple |
| --- | --- |
| `Read` | Peut ouvrir et consulter l'item |
| `Write` | Peut modifier l'item |
| `Reshare` | Peut repartager l'item à d'autres personnes |
| `Execute` | Peut lancer l'exécution d'un item exécutable |
| `ReadAll` | Peut lire l'ensemble des données ou contenus exposés par l'item selon son type |
| `ViewOutput` | Peut consulter les sorties produites |
| `ViewLogs` | Peut consulter les journaux d'exécution |
| `SubscribeOneLakeEvents` | Peut s'abonner aux événements OneLake liés à l'item si le scénario le permet |

1. Dans **Manage permissions**, repérer les permissions visibles dans votre environnement
2. **Read** ne veut pas dire automatiquement **modifier**
3. **Write** ne veut pas dire automatiquement **repartager**

**Ce que vous devez voir à l'écran** :

- Une liste de permissions plus fine qu'un simple rôle de workspace
- Une séparation claire entre lecture, modification, partage et exécution

### 1.7 - **ÉCHÉQUIER** : Combinaison Rôles Workspace × Permissions d'item sur Lakehouse

Cette section est l'une des plus importantes de l'atelier. Le rôle Workspace et les permissions d'item ne sont pas deux systèmes indépendants : ils **s'influencent mutuellement**, et le résultat observé n'est pas toujours intuitif. Les tests ci-dessous ont été réalisés en conditions réelles sur un tenant Fabric actif.

> ⚠️ **Attention** : le comportement réel peut différer de ce qu'on attendrait logiquement. C'est précisément l'intérêt pédagogique de cet échiquier.

#### Matrice des observations réelles (Lakehouse)

| Rôle Workspace | Permissions accordées (Lakehouse + Notebook) | Bouton Run Notebook | Accès SQL Analytics Endpoint | Accès Interface Lakehouse | Niveau global observé | Commentaire pédagogique |
| --- | --- | --- | --- | --- | --- | --- |
| **Viewer** | `Read` + `ViewOutput` | ❌   | ✅   | Limité | Lecture SQL seulement | Très restrictif — tables inaccessibles sans `ReadAll` |
| **Viewer** | `Read` + `ViewOutput` + `ReadAll` + `Execute` / Notebook : `Read` + `Edit` + `Run` | ❌ *(ou très tardif)* | ✅   | Limité | Lecture SQL OK, Run bloqué | **Même avec tous les droits item + Notebook, le rôle Viewer bloque le Run** |
| **Contributor** | `Read` + `Write` + `Reshare` + `Execute` + `ReadAll` + `ViewOutput` / Notebook : tous droits | ✅ *(après latence)* | ✅   | ✅   | Bon équilibre | Rôle le plus stable pour les démos — à privilégier en formation |
| **Member** | `Read` + `Write` + `Reshare` + `Execute` + `ReadAll` + `ViewOutput` / Notebook : tous droits | ❌   | ❌   | ✅ *(plus visible)* | Inattendu / Instable | **Perte du Run ET du SQL malgré des droits plus élevés qu'un Contributor** |
| **Admin** | Tous droits hérités | ✅   | ✅   | ✅ *(créer / supprimer)* | Accès total | Comportement normal d'administrateur |

#### Les règles à mémoriser

**1 — Le rôle Workspace est le facteur dominant.**  
Même avec `ReadAll`, `Execute`, `Run` et `Edit` accordés au niveau item, le rôle `Viewer` empêche l'exécution du Run. Les permissions d'item ne peuvent pas surclasser la limite imposée par le rôle.

**2 — Changer de rôle peut réinitialiser les permissions granulaires.**  
Passer un utilisateur de `Viewer` à `Contributor` ou `Member` peut écraser les permissions d'item déjà configurées. Revalider systématiquement après chaque changement de rôle.

**3 — `ReadAll` + `Execute` ciblent surtout le SQL Analytics Endpoint.**  
Ces permissions améliorent l'accès SQL mais ne garantissent pas l'exécution des Notebooks. Les plans Spark et SQL ont des mécanismes d'autorisation distincts.

**4 — Le comportement `Member` est contre-intuitif.**  
`Member` semble supérieur à `Contributor`, mais les tests montrent une perte du Run et du SQL Endpoint, alors que l'interface Lakehouse devient paradoxalement plus visible. À présenter comme une caractéristique réelle de Fabric, non comme un bug.

**5 — `Contributor` est le rôle à recommander en contexte de formation.**  
Meilleur équilibre entre accès Notebook, accès SQL et gestion des items, sans droits d'administration.

#### 1.7.1 Scénario 1 – État de base (le plus propre possible)

**Configuration testée :**

- Rôle Workspace : **Viewer**
- Permissions sur le Lakehouse : **Read + ViewOutput** uniquement

**Résultat observé :**

- Le compte test peut ouvrir le Lakehouse.
- Il peut ouvrir le **SQL analytics endpoint** et exécuter des requêtes.
- Il arrive à voir les données via le SQL endpoint (SELECT * FROM ... fonctionne).
- En revanche, dans l’interface Lakehouse (Tables / Files), il ne peut ni voir ni manipuler les données facilement.

**Conclusion :** Avec les permissions minimales (Read + ViewOutput), l’accès via SQL endpoint est déjà possible, mais l’expérience reste limitée en dehors du SQL.

### 1.7.2 Scénario 2 – Ajout de ReadAll

**Configuration testée :**

- Rôle Workspace : **Viewer**
- Permissions sur le Lakehouse : **Read + ViewOutput + ReadAll + Execute**

**Résultat observé :**

- Aucun changement notable par rapport au Scénario 1.
- Le compte test continue de pouvoir exécuter des requêtes dans le SQL endpoint et voir les données.
- L’ajout de ReadAll n’a pas modifié le comportement dans ce tenant pour le SQL endpoint.

**Conclusion :** Dans cet environnement, Read seul suffit déjà à lire les données via le SQL analytics endpoint. ReadAll n’apporte pas de bénéfice visible dans ce contexte précis.

### 1.7.3 Scénario 3 – Test via Spark (Notebook)

**Configuration testée :**

- Rôle Workspace : **Viewer**
- Permissions sur le Lakehouse : **Read + ViewOutput + ReadAll + Execute**

**Résultat observé :**

- Dans un Notebook attaché au Lakehouse, le bouton **Run** est **non visible**.
- Le compte test ne peut pas exécuter le Notebook, même avec ReadAll et Execute accordés sur le Lakehouse.

**Conclusion :** ReadAll et Execute sur le Lakehouse permettent l’accès via SQL, mais ne suffisent pas à exécuter un Notebook.

#### 1.7.4 Scénario 4 – Ajout de droits sur le Notebook (Viewer)

**Configuration testée :**

- Rôle Workspace : **Viewer**
- Permissions sur le Lakehouse : Read + Write + Reshare + Execute + ReadAll + ViewOutput
- Permissions sur le Notebook : Read + Edit + Share + Run

**Résultat observé :**

- Malgré tous les droits accordés sur le Notebook, le bouton **Run** reste invisible ou n’apparaît pas.
- Le compte test ne peut toujours pas exécuter le Notebook.

**Conclusion :** Avec le rôle **Viewer**, même en donnant toutes les permissions possibles sur le Notebook, l’exécution reste bloquée. Le rôle Workspace est le facteur limitant.

#### 1.7.5 Scénario 5 – Passage en Contributor

**Configuration testée :**

- Rôle Workspace : **Contributor**
- Permissions sur le Lakehouse : Read + Write + Reshare + Execute + ReadAll + ViewOutput
- Permissions sur le Notebook : Read + Edit + Run

**Résultat observé :**

- Le bouton **Run** du Notebook devient visible (parfois après rafraîchissement ou latence).
- Le compte test peut maintenant exécuter les cellules du Notebook avec succès.
- L’accès SQL endpoint reste disponible.

**Conclusion :** Le rôle **Contributor** débloque l’exécution des Notebooks. C’est actuellement le rôle le plus stable pour les démonstrations pratiques.

#### 1.7.6 Scénario 6 – Passage en Member

**Configuration testée :**

- Rôle Workspace : **Member**
- Permissions sur le Lakehouse : Read + Write + Reshare + Execute + ReadAll + ViewOutput + SubscribeOneLakeEvents

**Résultat observé :**

- Le bouton **Run** du Notebook **disparaît**.
- Le **SQL Analytics Endpoint** devient inaccessible.
- L’interface Lakehouse (Tables / Files) devient plus visible et accessible.

**Conclusion :** Le passage en **Member** produit un comportement inattendu et instable : perte d’accès au SQL endpoint et à l’exécution du Notebook, malgré des permissions larges.

#### 1.7.7 Scénario 7 – Passage en Admin

**Configuration testée :**

- Rôle Workspace : **Admin**
- Permissions sur le Lakehouse : Read + Write + Reshare + Execute + ReadAll + ViewOutput + ...

**Résultat observé :**

- Le bouton **Run** est visible.
- Le SQL Analytics Endpoint est accessible.
- Accès complet à l’interface Lakehouse (voir, créer, supprimer des tables, etc.).

**Conclusion :** Le rôle **Admin** donne un accès total, comme attendu.

## Partie 5 - Rôles DB : Built-in et Custom dans le Warehouse

Les rôles de base de données (**DB roles**) constituent une couche de sécurité intermédiaire entre les permissions SQL granulaires (GRANT/DENY individuels vus en Partie 4) et la gestion par workspace. Ils permettent de **regrouper des permissions sous un nom** et d’affecter des utilisateurs à ce groupe plutôt que de gérer les droits un par un.

Microsoft Fabric Warehouse expose les mêmes rôles fixes que SQL Server, accessibles dans l’explorateur sous **Security > DB roles (Built-in)**. Il permet également de créer des **rôles custom** via `CREATE ROLE`.

> **Référence officielle** : [SQL granular permissions in Microsoft Fabric](https://learn.microsoft.com/en-us/fabric/data-warehouse/sql-granular-permissions) — [Database-Level Roles (SQL Server)](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/database-level-roles)

### 5.1 - Présenter les rôles DB Built-in du Warehouse

#### Rôles visibles dans l’explorateur

| Rôle Built-in | Permissions effectives | Pertinence dans Fabric |
| --- | --- | --- |
| `db_owner` | Contrôle total : DDL, DML, sécurité, configuration | Complet — réservé aux administrateurs |
| `db_accessadmin` | Gère l’ajout/suppression d’utilisateurs dans la base | ⚠️ Limité — pas d’auth SQL dans Fabric (Entra ID uniquement) |
| `db_securityadmin` | GRANT / DENY / REVOKE, gestion des rôles (hors fixed roles) | Utile pour déléguer la gestion de la sécurité SQL |
| `db_ddladmin` | CREATE / ALTER / DROP d’objets — sans droits de sécurité | Typique pour un rôle "architecte data" |
| `db_backupoperator` | Exécuter des commandes BACKUP | ⚠️ Non applicable — BACKUP non disponible dans Fabric (SaaS) |
| `db_datareader` | SELECT sur toutes les tables et vues de la base | Lecture globale — attention aux données sensibles |
| `db_datawriter` | INSERT / UPDATE / DELETE sur toutes les tables | Écriture globale — à restreindre avec DENY si nécessaire |
| `db_denydatareader` | DENY SELECT explicite sur toutes les tables | Bloque tout accès lecture, même si `db_datareader` est accordé |
| `db_denydatawriter` | DENY INSERT/UPDATE/DELETE sur toutes les tables | Bloque toute écriture, même si `db_datawriter` est accordé |
| `public` | Rôle par défaut — tous les utilisateurs en sont membres | Toujours actif — ne pas y mettre de permissions |

> ⚠️ **Important Fabric** : `db_backupoperator` et `db_accessadmin` existent dans l’interface mais ont une utilité limitée dans Fabric. `db_backupoperator` notamment est sans effet car les commandes `BACKUP` ne sont pas disponibles dans un Warehouse Fabric (plateforme SaaS managée). Les mentionner à titre informatif sans les utiliser dans les démonstrations.

### 5.2 - Remise à zéro complète des permissions de la Partie 4

Avant d’entrer dans les DB roles, il est **indispensable de repartir d’un état vierge** pour les deux comptes. Les permissions GRANT et DENY posées individuellement en Partie 4 créeraient des conflits imprévisibles avec les rôles — notamment parce qu’un DENY explicite l’emporte toujours sur un GRANT de rôle.

> ⚠️ **Règle à retenir** : `REVOKE` supprime une entrée explicite (qu’elle soit GRANT ou DENY). Il ne "donne pas" et ne "bloque pas" — il efface. L’utilisateur revient à l’état neutre, sans aucune permission explicite pour l’objet concerné.

#### Explication : le mapping Rôle Workspace → permissions SQL implicites dans le Warehouse

Dans un Fabric Warehouse, le rôle Workspace n’est **pas seulement un contrôle d’accès à l’item** — il se traduit directement en permissions SQL à l’intérieur du moteur :

| Rôle Workspace | Permissions SQL implicites dans le Warehouse |
| --- | --- |
| **Admin** | Équivalent `db_owner` — contrôle total |
| **Member** | Lecture + écriture DML (SELECT, INSERT, UPDATE, DELETE) |
| **Contributor** | Lecture + écriture DML (SELECT, INSERT, UPDATE, DELETE) |
| **Viewer** | Lecture seule (SELECT uniquement) |

Un utilisateur **Contributor** a donc déjà des droits d’écriture implicites dans le Warehouse, **indépendamment de tout DB role**. Ajouter `db_datareader` à un Contributor ne restreint rien — au contraire, les droits hérités du workspace restent actifs.

> **Règle clé à retenir** : dans Fabric Warehouse, le rôle Workspace agit comme un **plancher de permissions**, pas comme un plafond. Un DB role ne peut pas restreindre ce que le rôle Workspace accorde — seul un `DENY` SQL explicite le peut.

### 5.9 - Comparaison : DB roles vs GRANT/DENY direct

| Critère | GRANT/DENY individuels (Partie 4) | DB Roles (custom ou built-in) |
| --- | --- | --- |
| Granularité | Maximum — objet par objet | Moyenne — définie au niveau du rôle |
| Maintenance | Complexe avec beaucoup d’utilisateurs | Simple — ajouter/retirer un membre |
| Réutilisabilité | Faible | Élevée — un rôle, N membres |
| Auditabilité | Via `sys.database_permissions` | Via `sys.database_role_members` + `sys.database_permissions` |
| Cas d’usage | Permissions très spécifiques par user | Groupes de profils (analyst, writer, admin) |
| Conflit DENY | DENY direct > GRANT de rôle | DENY de rôle > GRANT de rôle ou direct |

> **Message clé final** : dans un Warehouse Fabric, la bonne pratique est de **combiner les deux approches** — utiliser des rôles custom pour gérer les profils types, et ajouter des `DENY` directs pour les exceptions ou données particulièrement sensibles (ex. : `gold.margin_internal`).

### 6.1 - Créer la fonction de prédicat

La fonction de prédicat est le **cœur du mécanisme RLS**.

- **Ce qu'elle fait** : pour chaque ligne lue dans une table protégée, Fabric appelle cette fonction en lui passant la valeur de la colonne `Region` de cette ligne.
  
  - La fonction retourne `1` (= autoriser) si l'utilisateur connecté (`USER_NAME()`) figure dans la table `security.user_region_access` pour cette région ou s'il est `dev` (le formateur, qui voit tout).
    
  - La fonction retourne une table vide (= bloquer) dans tous les autres cas.
    
- **Ce qu'elle n'est pas** : ce n'est pas `un filtre classique` qu'on applique manuellement dans les requêtes. Une fois la security policy créée en 6.2,
  
  Fabric l'injecte **automatiquement et invisiblement** dans chaque `SELECT` sur les tables protégées — l'utilisateur ne voit que les lignes auxquelles il a droit, sans même savoir que le filtre existe.
  
- **Le lien avec nos données** : la table `security.user_region_access` (créée en Partie 3) contient le mapping `participant → Nord` et `test → Sud`. C'est cette table que la fonction interroge à chaque lecture pour décider quelles lignes sont visibles.
  

1. Ouvrir une nouvelle requête SQL
2. Coller :

```sql
CREATE FUNCTION security.fn_region_predicate(@Region AS NVARCHAR(20))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS fn_region_predicate_result
    WHERE EXISTS
    (
        SELECT 1
        FROM security.user_region_access AS ura
        WHERE ura.UserPrincipalName = USER_NAME()
          AND ura.Region = @Region
    )
    OR USER_NAME() = 'dev@contactemeraudeit.onmicrosoft.com';
GO
```

3. Cliquer sur **Run**

| Élément | Valeur |
| --- | --- |
| **Function name** | `security.fn_region_predicate` |
| **Principe** | Filtrer selon la région autorisée |

**Ce que vous devez voir à l'écran** :

- Une fonction créée avec succès

> **Résultat attendu** : le prédicat RLS est prêt.

## Partie 7 - Implémenter le Column-Level Security dans le Warehouse

### 7.0 - Remise à zéro avant le CLS : supprimer les objets RLS de la Partie 6

Le CLS (Column-Level Security) peut coexister techniquement avec le RLS, mais pour une démonstration claire, on démarre Partie 7 sans security policy active. Cela évite que le filtre de lignes (RLS) masque des résultats et complique la lecture des tests de colonnes.

> ⚠️ **Important — grants de colonnes à conserver** : les GRANT de la section 6.3 étaient des grants **au niveau colonne** (syntaxe `GRANT SELECT ON OBJECT (col1, col2...) TO [user]`), pas des grants table entière. Ils ne peuvent pas être révoqués par un simple `REVOKE SELECT ON OBJECT` — cela provoquerait l’erreur `Msg 15151 : Cannot find the object`. De plus, **ces permissions colonne sont exactement ce dont la démo CLS a besoin** — elles constituent le mécanisme lui-même. On ne les supprime pas : on se contente de supprimer la security policy RLS et sa fonction.

**Ce qu’on supprime / ce qu’on conserve :**

| Objet | Type | Action |
| --- | --- | --- |
| `security.RegionSecurityPolicy` | Security policy RLS | ✅ `DROP SECURITY POLICY` |
| `security.fn_region_predicate` | Fonction de prédicat RLS | ✅ `DROP FUNCTION` |
| GRANT colonnes `gold.sales_secure_detail` pour `participant` et `test` | Permissions colonne (CLS) | ⛔ **À conserver** — base de la démo Partie 7 |

1. Avec `dev`, exécuter uniquement la suppression des objets RLS :

```sql
-- Désactiver et supprimer la security policy RLS
IF EXISTS (
    SELECT 1 FROM sys.security_policies
    WHERE name = ‘RegionSecurityPolicy’
      AND SCHEMA_NAME(schema_id) = ‘security’
)
BEGIN
    ALTER SECURITY POLICY security.RegionSecurityPolicy WITH (STATE = OFF);
    DROP  SECURITY POLICY security.RegionSecurityPolicy;
END
GO

-- Supprimer la fonction de prédicat RLS
IF EXISTS (
    SELECT 1 FROM sys.objects
    WHERE name = ‘fn_region_predicate’
      AND SCHEMA_NAME(schema_id) = ‘security’
      AND type = ‘IF’
)
    DROP FUNCTION security.fn_region_predicate;
GO
```

2. Vérifier que les objets RLS sont bien supprimés et que les permissions colonne sont en place :

```sql
-- Vérifier security policies (doit retourner 0 ligne)
SELECT name, is_enabled
FROM sys.security_policies
WHERE name = ‘RegionSecurityPolicy’;

-- Vérifier la fonction (doit retourner 0 ligne)
SELECT name, type_desc
FROM sys.objects
WHERE name = ‘fn_region_predicate’;

-- Vérifier les permissions colonne sur gold.sales_secure_detail
-- Doit retourner les colonnes accordées à participant et test (minor_id > 0 = niveau colonne)
SELECT
    pr.name                          AS compte,
    dp.permission_name,
    dp.state_desc,
    COL_NAME(dp.major_id, dp.minor_id) AS colonne_accordee
FROM sys.database_permissions dp
JOIN sys.database_principals pr ON dp.grantee_principal_id = pr.principal_id
WHERE pr.name IN (
    ‘test@contactemeraudeit.onmicrosoft.com’,
    ‘participant@contactemeraudeit.onmicrosoft.com’
)
  AND dp.major_id = OBJECT_ID(‘gold.sales_secure_detail’)
  AND dp.minor_id > 0   -- minor_id > 0 = permission au niveau colonne
ORDER BY pr.name, dp.minor_id;
```

**Ce que vous devez voir à l’écran** :

- Les deux premières requêtes retournent **0 ligne** (RLS supprimé)
- La troisième retourne les colonnes accordées par compte — confirme que les permissions CLS sont bien en place et prêtes pour les tests Partie 7

> **Résultat attendu** : la security policy RLS est supprimée. Les grants de colonnes de la section 6.3 sont intacts et constituent la base de la démonstration CLS qui suit.

> **Résultat attendu** : aucune security policy active, aucune fonction RLS, aucune permission SQL directe. Le CLS sera configuré de zéro dans la section 7.1.

### 7.1 - Configurer et appliquer le CLS

**Principe** : `DENY SELECT ON OBJECT::table (colonne) TO [compte]` bloque une colonne précise. Le `DENY` est toujours prioritaire sur tout `GRANT`, y compris les permissions implicites du rôle Workspace — **à condition que le compte ne soit pas `db_owner`**.

> ⚠️ **Pourquoi utiliser `test` et non `participant`** : `participant` est Admin Workspace (= `db_owner`) — les membres de `db_owner` contournent tous les `DENY`. `test` est Viewer (pas `db_owner`) : le `DENY` s'applique correctement sur ce compte.

| Colonne | `test` (Viewer) | `participant` (Admin) |
| --- | --- | --- |
| Toutes colonnes | Oui (via rôle Viewer) | Oui (via Admin) |
| `CustomerEmail` | **Non** — DENY | Oui |

#### Étape 1 — Vérifier les rôles Workspace

Dans le portail Fabric → **Workspace settings → Manage access**, confirmer :

| Compte | Rôle attendu |
| --- | --- |
| `test@contactemeraudeit.onmicrosoft.com` | **Viewer** |
| `participant@contactemeraudeit.onmicrosoft.com` | Admin |

#### Étape 2 — Appliquer le DENY CLS

Avec `dev`, exécuter :

```sql
-- Bloquer la colonne sensible pour test
DENY SELECT ON OBJECT::gold.sales_secure_detail (CustomerEmail)
TO [test@contactemeraudeit.onmicrosoft.com];
```

> `participant` (Admin) voit toutes les colonnes par défaut — aucune action nécessaire.

#### Étape 3 — Vérifier les permissions

```sql

    dp.permission_name,
    dp.state_desc,
    COL_NAME(dp.major_id, dp.minor_id)  AS colonne_ciblee
FROM sys.database_permissions dp
JOIN sys.database_principals pr ON dp.grantee_principal_id = pr.principal_id
WHERE pr.name IN (
    'test@contactemeraudeit.onmicrosoft.com',
    'participant@contactemeraudeit.onmicrosoft.com'
)
  AND dp.major_id = OBJECT_ID('gold.sales_secure_detail')
  AND dp.minor_id > 0;
```

| `state_desc` | Signification |
| --- | --- |
| `DENY` | Colonne bloquée — prioritaire sur tout GRANT |
| `GRANT` | Colonne accordée explicitement |

**Ce que vous devez voir** :

- Une ligne `DENY` sur `CustomerEmail` pour `test`
- Aucune ligne pour `participant` (son accès complet vient du rôle Admin)
