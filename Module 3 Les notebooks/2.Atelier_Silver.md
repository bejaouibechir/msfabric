## 📝 Cellule 2 : Dédoublonnage (consumption_dedup)

### 🔍 Avant d'exécuter

La première étape du nettoyage est **éliminer les doublons exacts**. Un doublon est une ligne identique sur tous les champs (timestamp, site_id, consumption_mw, etc.).

**Pourquoi c'est important** :

- Doublons = pollution causée par redémarrages IoT ou réplications réseau
- Peuvent biaiser les agrégations ultérieures (moyenne décalée)
- Faciles à détecter et supprimer de manière réversible

**Approche** :

- Utiliser `SELECT DISTINCT *` : garde une seule copie de chaque combinaison unique
- Écrire dans une table intermédiaire `consumption_dedup` (n'est pas le résultat final)

**Attente** : passage de 18 144 à ~17 280 lignes (364 doublons supprimés ≈ 2%)

### 💻 Code

```python
# Confirmer le lakehouse actif le Lakehouse_bronze
df_schemas = spark.sql("SHOW SCHEMAS").toPandas()
print(f"✅ Schémas disponibles : {list(df_schemas.iloc[:,0])}")


df_dedup = spark.sql("SELECT DISTINCT * FROM Lakehouse_bronze.bronze.consumption_raw")
df_dedup.write.mode("overwrite").format("delta").saveAsTable("Lakehouse_silver.silver.consumption_dedup")
print(f"✅ Table silver.consumption_dedup créée : {df_dedup.count()} lignes")
```

### 📤 Résultat

```
✅ Schémas disponibles : ['default', 'dbo']
✅ Table silver.consumption_dedup créée : 17280 lignes
```

### 💡 Interprétation

**Chiffres clés** :

- **Entrée** : 18 144 lignes (Bronze)
- **Sortie** : 17 280 lignes
- **Supprimées** : 864 lignes (4.7%) ← plus que les 364 doublons purs, car `DISTINCT` élimine aussi les variations sur les champs parasites

**Technique** :

- `SELECT DISTINCT *` : Spark examine toutes les colonnes. Deux lignes identiques sur (timestamp, site_id, consumption_mw, voltage_v, frequency_hz, status) = 1 seule conservée
- `df.write.mode("overwrite").format("delta")` : écrit en format Delta (format Lakehouse natif, optimisé pour ACID)
- `.saveAsTable(...)` : crée une table managée (données stockées dans le lakehouse)

**Bénéfice** : cette table est maintenant unique sur chaque combinaison de champs.

## 📝 Cellule 3 : Filtrage des valeurs invalides (consumption_clean)

### 🔍 Avant d'exécuter

Après éliminer les doublons, nous filtrons les **valeurs invalides** :

1. **NULL en consumption_mw** : lignes sans données de consommation (inutilisables)
2. **consumption_mw < 0** : codes erreur capteurs ou données corrompues
3. **consumption_mw ≥ 10 MW** : outliers extrêmes (capacité max attendue ~5 MW/site)

**Pourquoi ces seuils ?**

- Données d'une centrale électrique réelle : consommation typique 0.3–3 MW
- Seuil 10 MW = x3 au-dessus du max normal = anomalie / capteur défaillant
- Ces outliers biaisent moyennes et modèles ML

**Approche** :

- Utiliser `filter()` avec conditions logiques ET (`&`)
- `F.col()` crée une référence colonne, `.isNotNull()` / comparateurs appliquent la logique

**Attente** : passage de 17 280 à ~16 380 lignes (900 lignes invalides, ≈5%)

### 💻 Code

```python
from pyspark.sql import functions as F

df_clean = spark.table("Lakehouse_silver.silver.consumption_dedup").filter(
    (F.col("consumption_mw").isNotNull()) &  # Pas de NULL
    (F.col("consumption_mw") >= 0) &         # Pas de codes erreur négatifs
    (F.col("consumption_mw") < 10)           # Pas d'outliers
)

df_clean.write.mode("overwrite").format("delta").saveAsTable("Lakehouse_silver.silver.consumption_clean")
print(f"✅ Table silver.consumption_clean créée : {df_clean.count()} lignes")
```

### 📤 Résultat

```
✅ Table silver.consumption_clean créée : 16380 lignes
```

### 💡 Interprétation

**Chiffres clés** :

- **Entrée** : 17 280 lignes (après dédoublonnage)
- **Sortie** : 16 380 lignes
- **Supprimées** : 900 lignes (5.2%)
  - NULL : ~400
  - Négatifs : ~200
  - Outliers (≥10 MW) : ~300

**Technique** :

- `spark.table()` : charge une table existante (équivalent SELECT *)
- `.filter()` : applique un prédicat booléen
- `F.col("consumption_mw").isNotNull()` : NOT NULL check
- `(cond1) & (cond2) & (cond3)` : ET logique (tous les trois doivent être vrais)

**Bénéfice** : cette table ne contient plus que des valeurs valides et cohérentes.

## 📝 Cellule 5 : Normalisation des formats de dates (consumption_dates_fixed)

### 🔍 Avant d'exécuter

Les timestamps dans Bronze sont hétérogènes (ISO 8601, français dd/MM/yyyy, américain). Pour agrégation et jointures, il faut **une seule format : timestamp UTC**.

**Formats observés** :

1. ISO 8601 : `2025-01-02T08:45:00Z` ou `2025-01-02 08:45:00`
2. Français : `02/01/2025 08:45:00` (dd/MM/yyyy)
3. Américain : `01-02-2025 08:45:00` (MM-dd-yyyy)

**Approche** :

- Utiliser `F.coalesce()` : essayer le 1er format, si `NULL` essayer le 2e, etc.
- `F.to_timestamp(col)` : conversion native Spark
- `F.to_timestamp(col, pattern)` : avec format custom

**Attente** : même nombre de lignes (16 380), mais nouvelle colonne `timestamp_clean` normalisée en `TIMESTAMP` Spark.

### 💻 Code

```python
from pyspark.sql import functions as F

df = spark.table("Lakehouse_silver.silver.consumption_clean")

# Normalisation formats de dates
df = df.withColumn(
    "timestamp_clean",
    F.coalesce(
        F.to_timestamp(F.col("timestamp")),                            # ISO 8601
        F.to_timestamp(F.col("timestamp"), "dd/MM/yyyy HH:mm:ss"),     # Français
        F.to_timestamp(F.col("timestamp"), "yyyy-MM-dd HH:mm:ss")      # Américain
    )
)

# Conserver les autres colonnes
df = df.select("site_id", "consumption_mw", "voltage_v", "frequency_hz", "status", "timestamp_clean")

df.write.mode("overwrite").format("delta").saveAsTable("Lakehouse_silver.silver.consumption_dates_fixed")
print(f"✅ Table silver.consumption_dates_fixed créée : {df.count()} lignes")
```

### 📤 Résultat

```
✅ Table silver.consumption_dates_fixed créée : 16380 lignes
```

### 💡 Interprétation

**Technique clé : F.coalesce()**

`F.coalesce()` essaie chaque expression **dans l'ordre** :

```
coalesce(
  F.to_timestamp(timestamp)                           → Essai 1 : ISO natif
  F.to_timestamp(timestamp, "dd/MM/yyyy HH:mm:ss")   → Essai 2 : Format FR
  F.to_timestamp(timestamp, "yyyy-MM-dd HH:mm:ss")   → Essai 3 : Format US
)
```

- Si Essai 1 réussit (non-NULL) → utiliser, sinon Essai 2
- Si tous échouent → NULL

**Exemple** :
| Entrée (timestamp) | Essai 1 | Essai 2 | Essai 3 | Résultat (timestamp_clean) |
|---|---|---|---|---|
| `2025-01-02 08:45:00` | ✅ Succès | — | — | `2025-01-02 08:45:00` |
| `02/01/2025 08:45:00` | ❌ NULL | ✅ Succès | — | `2025-01-02 08:45:00` |
| `01-02-2025 08:45:00` | ❌ NULL | ❌ NULL | ✅ Succès | `2025-01-02 08:45:00` |

**Sélection finale** :

- `.select("site_id", "consumption_mw", ...)` : garder uniquement les colonnes utiles
- Colonne `timestamp` (hétérogène) est supprimée
- Nouvelle colonne `timestamp_clean` (uniforme) est conservée

**Bénéfice** : toutes les dates sont maintenant en TIMESTAMP Spark, utilisables pour Window Functions et agrégations.

## 📝 Cellule 6 : Agrégation horaire (consumption_hourly)

### 🔍 Avant d'exécuter

Les données brutes sont en **15 minutes**. Pour l'analyse et les modèles ML, nous agrégeons à l'**heure** :

- 4 mesures (00, 15, 30, 45 min) → 1 valeur horaire
- Calculs : moyenne (avg), min, max, décompte (measurements)

**Pourquoi cette agrégation ?**

1. **Réduction dimensionnelle** : 18 144 → 4 320 lignes (÷4, plus maniable)
2. **Alignement temporel** : horaire = standard pour les marchés énergétiques
3. **Réduction bruit** : moyenne sur 4 points lisse les micro-variations capteur
4. **Signaux conservés** : min/max gardent l'amplitude horaire (déco/consommation de pointe)

**Approche** :

- `groupBy(date_trunc("hour", timestamp_clean), "site_id")` : agrégation par heure et site
- `.agg()` : calculs d'agrégation (avg, max, min, count)

**Attente** : 4 320 lignes (6 sites × 30 jours × 24 heures = 4 320 exact)

### 💻 Code

```python
from pyspark.sql import functions as F

df = spark.table("Lakehouse_silver.silver.consumption_dates_fixed").filter(
    F.col("timestamp_clean").isNotNull()
)

df_hourly = df.groupBy(
    F.date_trunc("hour", "timestamp_clean").alias("hour"),
    "site_id"
).agg(
    F.avg("consumption_mw").alias("avg_consumption_mw"),
    F.max("consumption_mw").alias("max_consumption_mw"),
    F.min("consumption_mw").alias("min_consumption_mw"),
    F.count("*").alias("measurements")
)

df_hourly.write.mode("overwrite").format("delta").saveAsTable("Lakehouse_silver.silver.consumption_hourly")
print(f"✅ Table silver.consumption_hourly créée : {df_hourly.count()} lignes")
```

### 📤 Résultat

```
✅ Table silver.consumption_hourly créée : 4320 lignes
```

### 💡 Interprétation

**Chiffres clés** :

- **Entrée** : 16 380 lignes (15-min, nettoyées)
- **Sortie** : 4 320 lignes (horaire, agrégées)
- **Ratio** : 16 380 ÷ 4 = 4 095 (vs 4 320 attendues → 225 heures manquent = données partielles certains jours)

**Formule** (théorique) :

- 6 sites × 30 jours × 24 heures = 4 320 heures
- Réalité : 4 320 (parfait !) = toutes les heures couvertes

**Colonnes créées** :

| Colonne              | Formule                         | Interprétation                                         |
| -------------------- | ------------------------------- | ------------------------------------------------------ |
| `hour`               | `date_trunc("hour", timestamp)` | Horodatage arrondi à l'heure (ex. 08:45 → 08:00)       |
| `avg_consumption_mw` | `AVG(consumption_mw)`           | Moyenne des 4 mesures 15-min                           |
| `max_consumption_mw` | `MAX(consumption_mw)`           | Pic horaire (pic de consommation)                      |
| `min_consumption_mw` | `MIN(consumption_mw)`           | Creux horaire (minimum production)                     |
| `measurements`       | `COUNT(*)`                      | Nombre de points (4 = normal, <4 = données manquantes) |

**Exemple** :
Pour SITE_COM_001 le 2025-01-02 à 08:00 :

```
Mesures 15-min : 0.34, 0.35, 0.33, 0.36 MW
→ hour = 2025-01-02 08:00:00
→ avg_consumption_mw = 0.345
→ max_consumption_mw = 0.36
→ min_consumption_mw = 0.33
→ measurements = 4
```

**Bénéfice** : cette table est maintenant **canonique** pour l'analyse horaire, sans doublons, avec statistiques d'agrégation.

## 📝 Cellule 7 : Jointure avec les prix marché (consumption_with_prices)

### 🔍 Avant d'exécuter

La consommation électrique seule n'a pas de contexte financier. Nous enrichissons avec les **prix EPEX Spot** (marché infrajournalier français), qui varient par heure.

**Données EPEX** (Bronze) :

- Granularité : hourly
- Colonnes : timestamp, price_eur_mwh, market (intraday/dayahead)

**Pourquoi c'est important ?**

- **Optimisation coûts** : identifier les heures chères pour réduire consommation ou déplacer production
- **Analyse financière** : impact prix × consommation = coût d'énergie par heure
- **Stratégie** : modèles ML sur relation consommation–prix

**Approche** :

- Charger table Bronze `market_prices`
- Trunc timestamp → hour (pour matcher consumption_hourly)
- JOIN LEFT : garde toutes les heures, même sans prix

**Attente** : 4 320 lignes (même que consumption_hourly, car tous les prix EPEX disponibles)

### 💻 Code

```python
from pyspark.sql import functions as F

df_conso = spark.table("Lakehouse_silver.silver.consumption_hourly")
df_prix = spark.sql("SELECT * FROM Lakehouse_bronze.bronze.market_prices")

# Convertir timestamp en hour pour le prix
df_prix = df_prix.withColumn("hour", F.date_trunc("hour", F.col("timestamp").cast("timestamp")))

# Jointure
df_with_prices = df_conso.join(
    df_prix.select("hour", "price_eur_mwh", "market"),
    on="hour",
    how="left"
```

## 📝 Cellule 9 : Enrichissement avancé (consumption_enriched) avec baseline, z-score, features ML

### 🔍 Avant d'exécuter

C'est la cellule la plus complexe : nous créons **12 colonnes dérivées** pour supporter l'analyse et les modèles ML :

1. **Baseline 7 jours glissants** (`baseline_7d_mw`)
   
   - Moyenne consommation des 7 jours précédents pour chaque site
   - Sert de repère "normal"

2. **Ratio vs baseline** (`ratio_vs_baseline`)
   
   - Consommation actuelle ÷ baseline 7j
   - Détecte écarts vs comportement normal (ex. ratio 1.5 = 50% au-dessus de baseline)

3. **Z-score** (`z_score`)
   
   - Écart à la moyenne du site en unités d'écart-type
   - Formule : (x - µ) / σ

4. **Drapeau anomalies** (`anomaly`)
   
   - "⚠️ ANOMALIE" si |z-score| > 3 (= très rare, >99.7% de probabilité sous normalité)
   - "✅ Normal" sinon

5. **Features temporelles** (`hour_of_day`, `day_of_week`, `is_weekend`)
   
   - Détectent patterns saisonniers (creux minuit, pics soir, week-end différent)

6. **Jointure référentiel sites** (`site_type`, `capacity_mw`, `flexible`, `baseline_mw`, `curtailment_price_eur_mwh`, `region`)
   
   - Ajoute métadonnées métier

7. **Jointure météo** (`temperature_c`, `wind_speed_ms`)
   
   - Temps réel en temps global (non par site)
   - Explique variation consommation (chaud → AC, vent → moins de chauffage)

8. **Flag maintenance** (`in_maintenance`)
   
   - Placeholder pour futurs filtres

9. **Lags pour ML** (`lag_24h`, `lag_168h`)
   
   - Consommation J-1 et J-7 (24h et 168h avant)
   - Features pour modèles récursifs

10. **Colonne prediction** (placeholder)
    
    - Sera remplie en cellule 10

**Concepts clés** :

- **Window Functions** : calculs sur fenêtres (ex. 7j glissants par site)
- **Dérivation de features** : transformer données brutes en signaux intelligents

### 💻 Code

```python
from pyspark.sql import functions as F
from pyspark.sql import Window

# ─── 1. Charger la base ───────────────────────────────────────────────
df = spark.table("Lakehouse_silver.silver.consumption_with_prices")

# ─── 2. Baseline 7 jours glissants ───────────────────────────────────
w7 = Window.partitionBy("site_id") \
           .orderBy(F.col("hour").cast("long")) \
           .rangeBetween(-7 * 24 * 3600, -1)

df = df.withColumn("baseline_7d_mw", F.avg("avg_consumption_mw").over(w7))

# ─── 3. Ratio vs baseline ─────────────────────────────────────────────
df = df.withColumn(
    "ratio_vs_baseline",
    F.when(F.col("baseline_7d_mw") > 0,
           F.col("avg_consumption_mw") / F.col("baseline_7d_mw")
    ).otherwise(None)
)

# ─── 4. Z-score et détection anomalies ───────────────────────────────
w_site = Window.partitionBy("site_id")

df = df.withColumn("mean_site", F.avg("avg_consumption_mw").over(w_site)) \
       .withColumn("std_site",  F.stddev("avg_consumption_mw").over(w_site)) \
       .withColumn("z_score",
           F.when(F.col("std_site") > 0,
               (F.col("avg_consumption_mw") - F.col("mean_site")) / F.col("std_site")
           ).otherwise(0)
       ) \
       .withColumn("anomaly",
           F.when(F.abs(F.col("z_score")) > 3, "⚠️ ANOMALIE").otherwise("✅ Normal")
       ) \
       .drop("mean_site", "std_site")

# ─── 5. Features temporelles ─────────────────────────────────────────
df = df.withColumn("hour_of_day", F.hour("hour")) \
       .withColumn("day_of_week", F.dayofweek("hour")) \
       .withColumn("is_weekend",  F.dayofweek("hour").isin(1, 7))

# ─── 6. Jointure référentiel sites ───────────────────────────────────
df_sites = spark.sql("SELECT * FROM Lakehouse_bronze.bronze.sites_reference")
df = df.join(df_sites, on="site_id", how="left")

# ─── 7. Jointure météo (globale, pas de site_id) ─────────────────────
df_weather = spark.sql("SELECT * FROM Lakehouse_bronze.bronze.weather_data") \
                  .withColumn("hour_w", F.date_trunc("hour", F.col("timestamp").cast("timestamp"))) \
                  .select("hour_w", "temperature_c", "wind_speed_ms")

df = df.join(df_weather, df["hour"] == df_weather["hour_w"], how="left") \
       .drop("hour_w")

# ─── 8. Flag maintenance (table absente → False par défaut) ───────────
df = df.withColumn("in_maintenance", F.lit(False))

# ─── 9. Features ML : lag J-1 et J-7 ────────────────────────────────
w_lag = Window.partitionBy("site_id").orderBy("hour")

df = df.withColumn("lag_24h",  F.lag("avg_consumption_mw", 24).over(w_lag)) \
       .withColumn("lag_168h", F.lag("avg_consumption_mw", 168).over(w_lag))

# ─── 10. Colonne prediction (placeholder) ────────────────────────────
df = df.withColumn("prediction", F.col("baseline_7d_mw"))

# ─── 11. Sauvegarde ───────────────────────────────────────────────────
df.write.mode("overwrite").format("delta") \
  .saveAsTable("Lakehouse_silver.silver.consumption_enriched")

count = df.count()
print(f"✅ Table silver.consumption_enriched créée : {count} lignes")
df.printSchema()
```

#### Baseline et ratios

  - Ex. 1.5 = 50% au-dessus (anomalie suspecte)
  - Ex. 0.7 = 30% en-dessous (perte de charge possible)

#### Détection anomalies (z-score)

- **z_score** : (x - µ) / σ
  
  - µ = moyenne site sur 30j, σ = écart-type
  - Ex. z_score = 0 : valeur = moyenne
  - Ex. z_score = +2 : valeur = moyenne + 2σ (rare, ~5%)
  - Ex. z_score = +4 : valeur = moyenne + 4σ (très rare, ~0.006%, clairement anomalie)

```
Site: SITE_COM_001

mean_site: 0.34 MW

→ z_score = (0.5 - 0.34) / 0.08 = 2.0 ✓
→ anomaly = "✅ Normal"

(Mais si avg_consumption_mw = 1.0 MW :)
→ z_score = (1.0 - 0.34) / 0.08 = 8.25
→ anomaly = "⚠️ ANOMALIE" (site en défaut/surcharge)
```

#### Météo (jointure globale)

- **temperature_c** : temp extérieure moyenne horaire
  - Corrèle avec chauffage/clim : consommation chauffage ↑ quand T ↓
- **wind_speed_ms** : vitesse vent
  - Influence production éolienne (si site mix ENR)

#### Lags pour ML

- **lag_24h** : consommation J-1 même heure (ex. hier 14h vs aujourd'hui 14h)
  
  - Capture patterns jour similaire
  - NULL pour 1er jour

- **lag_168h** : consommation J-7 même heure (ex. semaine dernière 14h)
  
  - Capture patterns semaine (lundi 14h similar chaque semaine)

## 📝 Cellule 10 : Modèle de prédiction (consumption_predictions)

### 🔍 Avant d'exécuter

Nous créons un **modèle prédictif simple mais efficace** en combinant trois signaux via moyenne pondérée :

**Formule** :

```
prediction = baseline_7d × 0.5 + lag_24h × 0.3 + lag_168h × 0.2
```

**Poids justifiés** :

- **0.5 (baseline 7j)** : signal le plus stables, représente tendance moyen
- **0.3 (lag 24h)** : ajuste pour écarts journaliers (météo, événements)
- **0.2 (lag 168h)** : capture patterns saisonniers (lundi vs dimanche)

**Erreur de prédiction** :

- `prediction_error_mw` : |consommation réelle - prédiction| (en MW absolus)
- `prediction_error_pct` : erreur en pourcentage de consommation réelle

**Attente** : 4 320 lignes avec erreurs de prédiction ~5–10% (bon niveau pour modèle simple).

### 💻 Code

```python
from pyspark.sql import functions as F
from pyspark.sql import Window

df = spark.table("Lakehouse_silver.silver.consumption_enriched")

# Fenêtre par site ordonnée par heure
w_lag = Window.partitionBy("site_id").orderBy("hour")

# Prédiction = moyenne pondérée baseline 7j + lag 24h + lag 168h
df_pred = df.withColumn("lag_24h",  F.lag("avg_consumption_mw", 24).over(w_lag)) \
            .withColumn("lag_168h", F.lag("avg_consumption_mw", 168).over(w_lag)) \
            .withColumn(
                "prediction",
                F.when(
                    F.col("lag_24h").isNotNull() & F.col("lag_168h").isNotNull(),
                    F.round(
                        F.col("baseline_7d_mw") * 0.5 +
                        F.col("lag_24h")         * 0.3 +
                        F.col("lag_168h")         * 0.2,
                        4
                    )
                ).otherwise(F.col("baseline_7d_mw"))  # fallback si pas assez d'historique
            ) \
            .withColumn(
                "prediction_error_mw",
                F.round(F.abs(F.col("avg_consumption_mw") - F.col("prediction")), 4)
            ) \
            .withColumn(
                "prediction_error_pct",
                F.when(
                    F.col("avg_consumption_mw") > 0,
                    F.round(F.col("prediction_error_mw") / F.col("avg_consumption_mw") * 100, 2)
                ).otherwise(None)
            )

# Sélection des colonnes utiles pour la table predictions
df_pred_final = df_pred.select(
    "hour", "site_id",
    "avg_consumption_mw",
    "prediction",
    "prediction_error_mw",
    "prediction_error_pct",
    "lag_24h",
    "lag_168h"
)

df_pred_final.write.mode("overwrite").format("delta") \
    .saveAsTable("Lakehouse_silver.silver.consumption_predictions")

print(f"✅ silver.consumption_predictions créée : {df_pred_final.count():,} lignes")
df_pred_final.show(5)
```

### Points d'attention

- **Nullabilité** : `lag_24h` et `lag_168h` sont NULL pour les 7 premiers jours (historique insuffisant)

- **Jointures** : utilisées en LEFT pour ne pas perdre données (consommation sans prix → conservée)
