## 📝 Cellule 7 : Jointure enriched + predictions (dataset Gold source)

### 🔍 Avant d'exécuter

La jointure fusionne deux vues complémentaires :
- **consumption_enriched** → réalité, anomalies, contexte
- **consumption_predictions** → prévisions, performance modèle

La clé de jointure est (`hour`, `site_id`). Un `left join` assure qu'aucune mesure réelle n'est perdue si une prédiction manque (graceful degradation).

Le **dataset fusionné** devient la matière première pour toutes les agrégations Gold.

### 💻 Code

```python
from pyspark.sql import functions as F

df = df_enriched.join(
    df_predictions.select("hour", "site_id",
                          F.col("prediction").alias("predicted_consumption_mw"),
                          "prediction_error_mw"),
    on=["hour", "site_id"],
    how="left"
)
print(f"📊 Dataset Gold source : {df.count():,} lignes")
df.select("hour", "site_id", "avg_consumption_mw",
          "predicted_consumption_mw", "prediction_error_mw", "anomaly", "price_eur_mwh").show(100)
```

## 📝 Cellule 8 : Agrégation journalière par site (df_daily + table gold.daily_consumption_by_site)

### 🔍 Avant d'exécuter

La première table Gold `daily_consumption_by_site` **agrège l'hourly en daily**. Cela :
- Réduit le volume de 4 320 à 180 lignes (180 = 6 sites × 30 jours)
- Recalcule des KPIs synthétiques : somme, moyenne, pic, écart de prédiction moyen
- Ajoute le contexte site (type, capacité) via jointure à `sites_reference`

**Cas d'usage métier** : Tableau de bord opérationnel quotidien, suivi de conformité, détection de dérives saisonnières.

### 💻 Code

```python
df_sites_ref = spark.table("Lakehouse_bronze.bronze.sites_reference")

# Dropper explicitement les colonnes dupliquées de df avant la jointure
cols_to_drop = [c for c in ["site_type", "capacity_mw", "region", "flexible"] if c in df.columns]
df = df.drop(*cols_to_drop)

# Jointure propre
df = df.join(
    df_sites_ref.select("site_id", "site_type", "capacity_mw", "region", "flexible"),
    on="site_id", how="left"
)

# Vérification
print("Colonnes après jointure:", df.columns)

df_daily = df.groupBy(
    F.to_date("hour").alias("date"),
    "site_id", "site_type", "capacity_mw"
).agg(
    F.sum("avg_consumption_mw").alias("total_consumption_mwh"),
    F.avg("avg_consumption_mw").alias("avg_consumption_mw"),
    F.max("max_consumption_mw").alias("peak_consumption_mw"),
    F.avg("baseline_7d_mw").alias("avg_baseline_mw"),
    F.avg("predicted_consumption_mw").alias("avg_predicted_mw"),
    F.avg("prediction_error_mw").alias("avg_prediction_error_mw"),
    F.avg("price_eur_mwh").alias("avg_price_eur_mwh"),
    F.max("price_eur_mwh").alias("peak_price_eur_mwh"),
    F.avg("temperature_c").alias("avg_temperature_c"),
    F.sum(F.when(F.col("anomaly") == "⚠️ ANOMALIE", 1).otherwise(0)).alias("nb_anomalies"),
    F.count("*").alias("nb_measurements")
).orderBy(F.desc("date"), "site_id")

print(f"✅ df_daily prêt : {df_daily.count()} lignes")
```

### 📤 Résultat

```
Colonnes après jointure: ['hour', 'site_id', 'avg_consumption_mw', 'site_type', 'capacity_mw', 'region', 'flexible', 'temperature_c', 'price_eur_mwh', 'predicted_consumption_mw', 'prediction_error_mw', 'anomaly', 'baseline_7d_mw', ...]
✅ df_daily prêt : 180 lignes
```

### 💡 Interprétation

- **180 lignes** = 6 sites × 30 jours : granularité quotidienne idéale pour reporting
- **Agrégats clés** :
  - `total_consumption_mwh` → énergie quotidienne (somme horaire)
  - `peak_consumption_mw` → pics de charge (max horaire)
  - `avg_predicted_mw` → prédiction moyenne jour

## 📝 Cellule 10 : KPIs mensuels par site (df_kpis)

### 🔍 Avant d'exécuter

À partir du daily, nous synthétisons un **KPI mensuel par site** :
- `total_consumption_month_mwh` — Énergie totale (facturation/compliance)
- `load_factor_pct` — Ratio (consommation / capacité) en %
- `anomaly_rate_pct` — Pourcentage d'heures anormales
- `prediction_error_pct` — Qualité du modèle en %
- `avg_electricity_price_eur_mwh` — Coût spot moyen

**Cas d'usage métier** : KPIs exécutifs, scoring de performance, benchmarking inter-sites.

Load factor = indicateur clé pour un gestionnaire de réseau :
- < 30 % → Site sous-utilisé ou favorable au délestage
- 50-70 % → Utilisation optimale
- > 80 % → Risque de saturation (nécessite investissements)

### 💻 Code

```python
df_kpis = df_daily.groupBy("site_id", "site_type", "capacity_mw").agg(
    F.sum("total_consumption_mwh").alias("total_consumption_month_mwh"),
    F.avg("avg_consumption_mw").alias("avg_consumption_mw"),
    F.round(F.avg("avg_consumption_mw") / F.col("capacity_mw") * 100, 2).alias("load_factor_pct"),
    F.round(F.sum("nb_anomalies") * 100.0 / F.sum("nb_measurements"), 2).alias("anomaly_rate_pct"),
    F.round(F.avg("avg_prediction_error_mw"), 3).alias("avg_prediction_error_mw"),
    F.round(F.avg("avg_prediction_error_mw") / F.avg("avg_consumption_mw") * 100, 1).alias("prediction_error_pct"),
    F.round(F.avg("avg_price_eur_mwh"), 2).alias("avg_electricity_price_eur_mwh"),
    F.countDistinct("date").alias("nb_days")
).orderBy(F.desc("total_consumption_month_mwh"))
```

### 📤 Résultat

DataFrame de 6 lignes (un KPI par site), trié par consommation décroissante

### 💡 Interprétation

Les KPIs seront rangés par importance énergétique :
1. SITE_IND_001 (industriel gros consommateur)
2. SITE_IND_002 (industriel)
3. SITE_COM_001 / COM_002 (commerciaux)
4. SITE_RES_001 / RES_002 (résidentiels)

Les anomaly_rate et prediction_error_pct servir à un **system health check** mensuel.

## 📝 Cellule 15 : Calcul du potentiel d'effacement (curtailment)

### 🔍 Avant d'exécuter

Pour chaque heure eligible, nous calculons :

1. **ratio_vs_baseline** = consommation réelle / baseline 7j
   - > 1 : surcharge → opportunité d'effacement forte
   - ~1 : charge normale → effacement moins pertinent

2. **curtailment_potential_mw** = 30 % de réduction max (standard industrie)
   - Un site ne peut pas réduire de plus de 30 % sans risque opérationnel

3. **potential_gain_eur** = économie financière si effacement
   - Formule : (MW réduit) × (Prix_spot - Prix_effacement_contracué)
   - Prix_effacement = seuil contractuel (102 €/MWh IND_001, 116 €/MWh IND_002)

4. **action_signal** = recommandation opérationnelle (🔴/🟠/🟢)
   - Dépend du prix instantané

### 💻 Code

```python
df_curtailment = df_flex.withColumn(
    "ratio_vs_baseline",
    F.round(F.col("avg_consumption_mw") / F.col("baseline_7d_mw"), 2)
).withColumn(
    "curtailment_potential_mw",
    F.round(F.col("avg_consumption_mw") * 0.3, 3)         # 30% effacement
).withColumn(
    "potential_gain_eur",
    F.when(
        F.col("price_eur_mwh") > F.col("curtailment_price_eur_mwh"),
        F.round((F.col("avg_consumption_mw") * 0.3) *
                (F.col("price_eur_mwh") - F.col("curtailment_price_eur_mwh")), 2)
    ).otherwise(0)
).withColumn(
    "action_signal",
    F.when(F.col("price_eur_mwh") > 300, "🔴 EFFACEMENT MAX")
     .when(F.col("price_eur_mwh") > 200, "🟠 EFFACEMENT PARTIEL")
     .when(F.col("price_eur_mwh") < 50,  "🟢 CONSOMMER")
     .otherwise("⚪ Surveiller")
)
```

### 📤 Résultat

(Colones ajoutées au DataFrame, pas d'affichage direct)

### 💡 Interprétation

Les nouvelles colonnes permettent une **prise de décision automatisée** :
- **🔴 EFFACEMENT MAX** : Crise énergétique, réduire immédiatement → signale aux opérateurs
- **🟠 EFFACEMENT PARTIEL** : Prix élevé, effacement optionnel mais rentable
- **🟢 CONSOMMER** : Électricité bon marché, maintenir charge complète
- **⚪ Surveiller** : Situation stable, attendre nouvelles conditions

**Exemple chiffré** :
- SITE_IND_001, heure H : consommation 2,5 MW, prix spot 250 €/MWh, prix_contrat 102 €/MWh
- Potentiel réduction : 2,5 × 0,3 = 0,75 MW
- Gain potentiel : 0,75 × (250 - 102) = **111 €** cette heure uniquement
- Signal : 🟠 EFFACEMENT PARTIEL

## 📝 Cellule 19 : Qualification et priorisation des alertes

### 🔍 Avant d'exécuter

Les alertes brutes sont transformées en **tickets actionnables** :

1. **alert_type** — Catégorie métier (diagnostic rapide)
   - "Consommation anormale" → Équipe technique (vérifier site)
   - "Prix spot très élevé" → Équipe trading (opportunité effacement)
   - "Erreur prédiction élevée" → Data science (affiner modèle)

2. **priority** — Escalade
   - CRITIQUE : Anomalie + prix > 300 → action immédiate
   - HAUTE : Soit anomalie soit prix élevé
   - MOYENNE : Erreur prédiction isolée
   - BASSE : Autres cas

Cette approche garantit que **l'opérateur voit d'abord** les situations nécessitant une décision rapide.

### 💻 Code

```python
df_alerts = df_alerts.withColumn(
    "alert_type",
    F.when(F.col("anomaly") == "⚠️ ANOMALIE", "Consommation anormale")
     .when(F.col("price_eur_mwh") > 300,        "Prix spot très élevé")
     .when(F.col("prediction_error_mw") > 1.0,  "Erreur prédiction élevée")
     .otherwise("Autre")
).withColumn(
    "priority",
    F.when((F.col("anomaly") == "⚠️ ANOMALIE") & (F.col("price_eur_mwh") > 300), "CRITIQUE")
     .when((F.col("anomaly") == "⚠️ ANOMALIE") | (F.col("price_eur_mwh") > 300), "HAUTE")
     .when(F.col("prediction_error_mw") > 1.0, "MOYENNE")
     .otherwise("BASSE")
)
```

### 📤 Résultat

(Colonnes ajoutées au DataFrame)

### 💡 Interprétation

Chaque alerte porte désormais :
- **Type explicite** → dirigé vers le bon département
- **Priority** → CRITICAL au sommet du backlog opérationnel

Exemple :
- Heure X : SITE_IND_001, anomalie détectée, prix 320 €/MWh → CRITIQUE (anomalie anormale pendant crise)
- Heure Y : SITE_RES_001, erreur prédiction 1,2 MW, prix 75 €/MWh → MOYENNE (problème préd isolé, pas urgent)
