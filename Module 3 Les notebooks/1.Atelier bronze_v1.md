## 📝 Cellule 1 : Configuration, vérification Spark et création du schéma bronze

### 🔍 Avant d'exécuter

**Objectif** : Vérifier que l'environnement Spark est opérationnel, puis créer le schéma `bronze` dans le Lakehouse.

**Pourquoi créer un schéma ?** Dans Microsoft Fabric, un Lakehouse organise ses tables en **schémas** (comme des dossiers pour les tables). Tout le code de cet atelier utilise la notation `bronze.nom_table` — si le schéma `bronze` n'existe pas, toutes les cellules suivantes échoueront avec l'erreur `Schema 'bronze' does not exist`.

> ⚠️ **Cette cellule doit être exécutée en premier**, avant toute création de table.

### 💻 Code

```python
# Vérifier que Spark est disponible
print(f"✅ Spark version: {spark.version}")

# Créer le schéma bronze s'il n'existe pas encore
spark.sql("CREATE SCHEMA IF NOT EXISTS bronze")
print("✅ Schéma bronze prêt")

# Confirmer le lakehouse actif
df_schemas = spark.sql("SHOW SCHEMAS").toPandas()
print(f"✅ Schémas disponibles : {list(df_schemas.iloc[:,0])}")
```

### 📤 Résultat

```
✅ Spark version: 3.5.5.5.4.20251218.3
✅ Schéma bronze prêt
✅ Schémas disponibles : ['bronze', 'default', 'dbo']
```

### 💡 Interprétation

✅ **Environnement validé** : Spark fonctionne et le schéma `bronze` est créé dans `Lakehouse_bronze`.

**Point clé** : `CREATE SCHEMA IF NOT EXISTS` est idempotent — vous pouvez relancer le notebook sans risque d'erreur si le schéma existe déjà.

## 📝 Cellule 2 : Import consumption_raw.csv

### 🔍 Avant d'exécuter

**Objectif** : Charger le fichier CSV de consommation brute et créer une table Delta dans le schéma bronze. Cette table contiendra **TOUTES** les données, y compris les erreurs.

**Variables et concepts clés** :

- `spark.read.csv()` : Lit un fichier CSV en parallèle (distribué sur plusieurs nœuds Spark)
- `option("inferSchema", "true")` : Spark détecte automatiquement les types de colonnes (string, int, double, etc.)
- `.format("delta")` : Format Delta Lake (ACID, time travel, optimisations)
- `bronze.consumption_raw` : Notation schéma.table dans le lakehouse

### 💻 Code

```python
# Charger le CSV avec PySpark
df_consumption = spark.read.format("csv") \
    .option("header", "true") \
    .option("inferSchema", "true") \
    .load("Files/data_bronze_notebooks/consumption_raw.csv")

# Compter les lignes avant écriture
nb_lignes = df_consumption.count()

# Créer la table dans le schéma bronze
df_consumption.write.mode("overwrite").format("delta").saveAsTable("bronze.consumption_raw")

print(f"✅ Table bronze.consumption_raw créée : {nb_lignes} lignes")
```

### 📤 Résultat

```
✅ Table bronze.consumption_raw créée : 18144 lignes
```

### 💡 Interprétation

📊 **Volume de données** : 18,144 lignes correspondent à ~30 jours de données pour 6 sites avec mesures toutes les 15 minutes :

- Calcul : 6 sites × 4 mesures/heure × 24h × 30j ≈ 17,280 lignes théoriques
- Les 864 lignes supplémentaires sont des **doublons** (retransmissions réseau)

✅ **Succès de l'opération** : La table Delta est créée et accessible via SQL. Le format Delta garantit :

- **Atomicité** : Soit tout est écrit, soit rien
- **Traçabilité** : Historique des versions (time travel)
- **Optimisations** : Compression, indexation automatique

⚠️ **Attention** : Ce nombre inclut les doublons et erreurs. C'est **NORMAL** en Bronze – on nettoiera en Silver.

## 📝 Cellule 4 : Détection des problèmes de qualité

### 🔍 Avant d'exécuter

**Objectif** : Quantifier les problèmes de qualité pour préparer le nettoyage Silver. Cette analyse diagnostique est cruciale pour anticiper les transformations nécessaires.

**Métriques calculées** :

- `total_rows` : Nombre total de lignes
- `unique_rows` : Lignes uniques (timestamp, site_id)
- `duplicates` : Doublons (retransmissions réseau)
- `null_values` : Valeurs NULL (capteur défaillant)
- `error_codes` : Codes erreur négatifs (-999, -888, -777)
- `outliers` : Valeurs aberrantes (> 10 MW au-delà de la capacité)

### 💻 Code

```sql
%%sql
-- Compter les NULL, codes erreur, doublons
SELECT 
    COUNT(*) as total_rows,
    COUNT(DISTINCT timestamp, site_id) as unique_rows,
    COUNT(*) - COUNT(DISTINCT timestamp, site_id) as duplicates,
    SUM(CASE WHEN consumption_mw IS NULL THEN 1 ELSE 0 END) as null_values,
    SUM(CASE WHEN consumption_mw < 0 THEN 1 ELSE 0 END) as error_codes,
    SUM(CASE WHEN consumption_mw > 10 THEN 1 ELSE 0 END) as outliers
FROM bronze.consumption_raw
```

### 📤 Résultat

| total_rows | unique_rows | duplicates | null_values | error_codes | outliers |
| ---------- | ----------- | ---------- | ----------- | ----------- | -------- |
| **18144**  | **17280**   | **864**    | **554**     | **319**     | **27**   |

### 💡 Interprétation détaillée

📊 **Analyse quantitative** :

- **864 doublons (4.8%)** : Retransmissions réseau typiques des capteurs IoT. À supprimer en Silver via `DISTINCT`.

- **554 NULL (3.1%)** : Capteurs défaillants temporairement. Options :
  
  - Interpolation linéaire si < 5% manquant par site
  - Suppression si criticité faible

- **319 codes erreur (1.8%)** : Codes `-999`/`-888`/`-777` envoyés par les capteurs en mode dégradé. À filtrer systématiquement.

- **27 outliers (0.1%)** : Pics > 10 MW alors que capacité max = 5 MW. Probablement :
  
  - Erreurs de calibration capteur
  - Bugs firmware
  - À investiguer manuellement si > 0.5%

✅ **Qualité globale** : **9.8%** de données problématiques (~1,764 lignes).

C'est **dans la norme** pour des données IoT brutes. Le taux de perte après nettoyage devrait être **< 10%**.

🎯 **Actions Silver priorisées** :

- **Priorité 1** : Doublons et codes erreur (faciles, règles simples)
- **Priorité 2** : NULL et outliers (nécessitent analyse métier)
