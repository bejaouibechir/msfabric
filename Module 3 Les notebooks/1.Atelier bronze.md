```python
print("✅ Schéma bronze prêt")

# Confirmer le lakehouse actif
df_schemas = spark.sql("SHOW SCHEMAS").toPandas()
print(f"✅ Schémas disponibles : {list(df_schemas.iloc[:,0])}")
```

## 📝 Cellule 7 : Détection rapide des problèmes de qualité

### 🔍 Avant d'exécuter

**Objectif** : Quantifier les problèmes de qualité en une seule requête SQL pour prioriser les actions Silver.

### 💻 Code

```sql
%%sql
SELECT
    COUNT(*)                                                    AS total_rows,
    COUNT(DISTINCT timestamp, site_id)                         AS unique_rows,
    COUNT(*) - COUNT(DISTINCT timestamp, site_id)              AS duplicates,
    SUM(CASE WHEN consumption_mw IS NULL THEN 1 ELSE 0 END)   AS null_values,
    SUM(CASE WHEN consumption_mw < 0 THEN 1 ELSE 0 END)       AS error_codes,
    SUM(CASE WHEN consumption_mw > 10 THEN 1 ELSE 0 END)      AS outliers
FROM bronze.consumption_raw
```

### 📤 Résultat

| total_rows | unique_rows | duplicates | null_values | error_codes | outliers |
| ---------- | ----------- | ---------- | ----------- | ----------- | -------- |
| **18,144** | **17,280**  | **864**    | **554**     | **319**     | **27**   |

### 💡 Interprétation

| Problème     | Volume | %    | Action Silver                             |
| ------------ | ------ | ---- | ----------------------------------------- |
| Doublons     | 864    | 4.8% | `DISTINCT` sur (timestamp_parsé, site_id) |
| NULL         | 554    | 3.1% | Filtrage + documentation                  |
| Codes erreur | 319    | 1.8% | Filtre `consumption_mw < 0`               |
| Outliers     | 27     | 0.1% | Comparaison avec `capacity_mw`            |

✅ **Qualité globale** : 9.8% de données problématiques — dans la norme IoT industrielle.

## 📝 Cellule 17 : Métadonnées Delta — détail technique des tables

### 🔍 Avant d'exécuter

**Objectif** : Inspecter les métadonnées Delta Lake pour chaque table : nombre de fichiers Parquet, taille de stockage, colonnes de partition.

**Commande** : `DESCRIBE DETAIL` est une commande Delta Lake native disponible en Spark SQL dans Fabric.

### 💻 Code

```python
from pyspark.sql import functions as F

tables_bronze = [
    "bronze.consumption_raw",
    "bronze.market_prices",
    "bronze.weather_data",
    "bronze.sites_reference",
    "bronze.maintenance_events"
]

print(f"{'Table':<30} {'Fichiers Parquet':>18} {'Taille (Ko)':>14} {'Partitions':>12}")
print("-" * 80)

for table in tables_bronze:
    detail = spark.sql(f"DESCRIBE DETAIL {table}").collect()[0]
    num_files  = detail["numFiles"]
    size_bytes = detail["sizeInBytes"]
    size_ko    = round(size_bytes / 1024, 1)
    partitions = detail["partitionColumns"] or "Aucune"
    print(f"{table:<30} {num_files:>18} {size_ko:>14,.1f} {str(partitions):>12}")
```

### 📤 Résultat

```
Table                          Fichiers Parquet     Taille (Ko)   Partitions
--------------------------------------------------------------------------------
bronze.consumption_raw                        8         4,312.4       Aucune
bronze.market_prices                          2           198.7       Aucune
bronze.weather_data                           1            42.3       Aucune
bronze.sites_reference                        1             1.2       Aucune
bronze.maintenance_events                     1             2.1       Aucune
```

### 💡 Interprétation

`consumption_raw` est fragmentée en **8 fichiers Parquet** — Spark a distribué l'écriture sur plusieurs partitions pour paralléliser. Les tables légères (sites, maintenance) tiennent en **1 seul fichier**. Aucune partition explicite n'a été définie (normal pour un import Bronze brut).

## 📝 Cellule 21 : Profil statistique des colonnes numériques de consommation

### 🔍 Avant d'exécuter

**Objectif** : Calculer les statistiques descriptives complètes de `consumption_mw` — min, max, moyenne, écart-type, percentiles 5 et 95.

> ⚠️ On travaille sur la table Delta déjà créée — aucune modification possible.

### 💻 Code

```python
from pyspark.sql import functions as F

df_conso = spark.table("bronze.consumption_raw").filter(F.col("consumption_mw") > 0)

print("📊 Profil statistique — consumption_mw (valeurs > 0 uniquement)")
df_conso.select(
    F.round(F.min("consumption_mw"), 3).alias("min_mw"),
    F.round(F.max("consumption_mw"), 3).alias("max_mw"),
    F.round(F.avg("consumption_mw"), 3).alias("avg_mw"),
    F.round(F.stddev("consumption_mw"), 4).alias("stddev_mw"),
    F.round(F.percentile_approx("consumption_mw", 0.05), 3).alias("p5_mw"),
    F.round(F.percentile_approx("consumption_mw", 0.95), 3).alias("p95_mw")
).show()
```

| 0.001  | 14.287 | 0.847  | 0.463     | 0.152 | 1.821  |

### 💡 Interprétation

- **p95 = 1.821** : 95% des mesures valides sont sous 1.821 MW — la distribution est asymétrique à droite

## 📝 Cellule 22 : Profil tension et fréquence réseau

### 🔍 Avant d'exécuter

**Objectif** : Profiler `voltage_v` et `frequency_hz` — indicateurs de **stabilité réseau électrique**. Ces colonnes sont absentes de la plupart des analyses de base mais cruciales pour un contexte smart-grid.

## 📝 Cellule 24 : Détection des formats de dates multiples

### 🔍 Avant d'exécuter

**Objectif** : Quantifier précisément les 3 formats de dates présents dans `timestamp` via expressions régulières. Ce problème est l'un des plus fréquents en ingestion IoT industrielle.

> 🔒 Analyse en lecture seule — on détecte les formats sans modifier la colonne `timestamp` (output Bronze intouché).

### 💻 Code

```python
df_raw = spark.table("bronze.consumption_raw")

df_formats = df_raw.select(
    F.when(F.col("timestamp").rlike(r"^\d{2}/\d{2}/\d{4}"),    "DD/MM/YYYY HH:MM:SS (européen)")
     .when(F.col("timestamp").rlike(r"^\d{4}-\d{2}-\d{2}T"),   "YYYY-MM-DDTHH:MM:SS (ISO 8601)")
     .when(F.col("timestamp").rlike(r"^\d{4}-\d{2}-\d{2} "),   "YYYY-MM-DD HH:MM:SS (ISO sans T)")

     .alias("format_detecte")
)

df_formats.groupBy("format_detecte") \
    .count() \
    .withColumn("pourcentage", F.round(F.col("count") / 18144 * 100, 1)) \
    .orderBy("count", ascending=False).show(truncate=False)

```

## 📝 Cellule 27 : Détection des trous temporels par site

### 🔍 Avant d'exécuter

**Objectif** : Identifier les **gaps temporels** — écarts entre deux mesures consécutives supérieurs à l'intervalle attendu (15 minutes). Un gap indique une perte de données ou une panne capteur.

**Technique** : Fenêtre Spark (`Window.partitionBy`) pour calculer le timestamp précédent par site.

### 💻 Code

```python
from pyspark.sql import Window, functions as F

# Parsing multi-format des timestamps
df_ts = spark.table("bronze.consumption_raw").withColumn(
    "ts",
    F.coalesce(
        F.to_timestamp("timestamp", "yyyy-MM-dd'T'HH:mm:ss"),
        F.to_timestamp("timestamp", "yyyy-MM-dd HH:mm:ss"),
        F.to_timestamp("timestamp", "dd/MM/yyyy HH:mm:ss")
    )
).filter(F.col("ts").isNotNull())

# Fenêtre : timestamp précédent par site
window_spec = Window.partitionBy("site_id").orderBy("ts")

df_gaps = df_ts \
    .withColumn("prev_ts", F.lag("ts", 1).over(window_spec)) \
    .withColumn("gap_minutes", (F.unix_timestamp("ts") - F.unix_timestamp("prev_ts")) / 60) \
    .filter(F.col("gap_minutes") > 15)  # Seuil : écart > 15 min

print("⏱️  Trous temporels détectés (écart > 15 min) par site :")
df_gaps.groupBy("site_id").agg(
    F.count("gap_minutes").alias("nb_trous"),
    F.round(F.max("gap_minutes"), 0).alias("ecart_max_min"),
    F.round(F.avg("gap_minutes"), 1).alias("ecart_moyen_min")
).orderBy("nb_trous", ascending=False).show()
```

### 📤 Résultat

| site_id      | nb_trous | ecart_max_min | ecart_moyen_min |
| ------------ | -------- | ------------- | --------------- |
| SITE_COM_001 | 3        | 30.0          | 25.0            |
| SITE_IND_002 | 2        | 30.0          | 30.0            |
| SITE_RES_001 | 1        | 45.0          | 45.0            |

### 💡 Interprétation

Les trous détectés correspondent principalement aux événements de maintenance (arrêt du capteur). Un écart de 30 min = saut d'**une mesure**. Un écart de 45 min = saut de **deux mesures**. Ces lacunes seront documentées dans le plan Silver mais **non interpolées** (règle Bronze).

## 📝 Cellule 34 : Ranking fiabilité capteurs

```python

    F.sum(F.when(F.col("consumption_mw").isNull(), 1).otherwise(0)).alias("nb_null"),

 .withColumn("score_fiabilite_pct",
    F.round((1 - (F.col("nb_null") + F.col("nb_erreur") + F.col("nb_doublons")) / F.col("total")) * 100, 1)
 ) \
 .withColumn("taux_null_pct",    F.round(F.col("nb_null") / F.col("total") * 100, 1)) \
 .withColumn("taux_erreur_pct",  F.round(F.col("nb_erreur") / F.col("total") * 100, 1)) \
```

### Requête 9.1 — Anomalies par site

**Interprétation de la requête :**

Cette requête SQL analyse les anomalies dans les données de consommation électrique par site.

Elle filtre les enregistrements ayant au moins une anomalie :

- `consumption_mw` NULL ou négatif (< 0)
- Tension hors norme (< 207V ou > 253V)
- Fréquence hors norme (|50 Hz - frequency_hz| > 0,5 Hz)

Puis elle compte, pour chaque `site_id` :

- Le nombre total d’anomalies (`nb_anomalies`)
- La répartition par type : nulls, codes erreur, tensions anormales, fréquences anormales

```sql
-- Endpoint T-SQL : bronze.consumption_raw
SELECT
    site_id,
    COUNT(*)                                                          AS nb_anomalies,
    SUM(CASE WHEN consumption_mw IS NULL THEN 1 ELSE 0 END)          AS nb_null,
    SUM(CASE WHEN consumption_mw < 0     THEN 1 ELSE 0 END)          AS nb_codes_erreur,
    SUM(CASE WHEN voltage_v < 207 OR voltage_v > 253 THEN 1 ELSE 0 END) AS nb_tension_anomale,
    SUM(CASE WHEN ABS(frequency_hz - 50) > 0.5 THEN 1 ELSE 0 END)   AS nb_freq_anomale
FROM [Lakehouse_bronze].[bronze].[consumption_raw]
WHERE consumption_mw IS NULL OR consumption_mw < 0
   OR voltage_v < 207 OR voltage_v > 253
   OR ABS(frequency_hz - 50) > 0.5
GROUP BY site_id
ORDER BY nb_anomalies DESC;
```

### 📤 Résultat attendu

| site_id      | nb_anomalies | nb_null | nb_codes_erreur | nb_tension_anomale | nb_freq_anomale |
| ------------ | ------------ | ------- | --------------- | ------------------ | --------------- |
| SITE_IND_001 | 246          | 91      | 54              | 64                 | 37              |

**Résultat :** les sites sont classés du plus problématique au moins problématique.

**En résumé :** elle identifie et quantifie les sites les plus défaillants en termes de qualité des mesures.

### Requête 9.2 — Anomalies par heure de la journée

**Interprétation de la requête :**

Cette requête analyse **à quelle heure de la journée** apparaissent le plus d’anomalies de consommation.

Elle filtre uniquement les lignes où `consumption_mw` est **NULL** ou **négatif** (< 0), puis extrait l’heure (0 à 23) à partir de la colonne `timestamp`.

Elle compte le nombre d’anomalies par heure et classe les heures de la plus problématique à la moins problématique.



```sql
SELECT
    DATEPART(HOUR, TRY_CAST(timestamp AS DATETIME2)) AS heure,
    COUNT(*) AS nb_anomalies
FROM [Lakehouse_bronze].[bronze].[consumption_raw]
WHERE consumption_mw IS NULL OR consumption_mw < 0
GROUP BY DATEPART(HOUR, TRY_CAST(timestamp AS DATETIME2))
ORDER BY nb_anomalies DESC;
```

**En résumé :** elle permet d’identifier les heures de la journée où les erreurs de mesure (null ou négatif) sont les plus fréquentes.

> `TRY_CAST` gère les formats de dates invalides sans lever d'erreur — équivalent T-SQL du `coalesce(to_timestamp(...))` Spark.

### Requête 9.3 — Distribution consommation journalière

**Interprétation de la requête :**

Cette requête calcule les statistiques de consommation électrique **par jour** l.

Elle ne garde que les mesures valides (`consumption_mw > 0`), puis pour chaque date :

- `jour` : la date (sans l’heure)
- `conso_moy_mw` : consommation moyenne en MW (arrondie à 3 décimales)
- `conso_totale_mw` : consommation totale de la journée en MW (arrondie à 2 décimales)
- `nb_mesures` : nombre de mesures valides ce jour-là

Résultat trié par date croissante.



```sql
SELECT
    CAST(TRY_CAST(timestamp AS DATETIME2) AS DATE)  AS jour,
    ROUND(AVG(CAST(consumption_mw AS FLOAT)), 3)    AS conso_moy_mw,
    ROUND(SUM(CAST(consumption_mw AS FLOAT)), 2)    AS conso_totale_mw,
    COUNT(*)                                         AS nb_mesures
FROM [Lakehouse_bronze].[bronze].[consumption_raw]
WHERE consumption_mw > 0
GROUP BY CAST(TRY_CAST(timestamp AS DATETIME2) AS DATE)
ORDER BY jour;
```

**En résumé :** elle donne un aperçu quotidien de la consommation moyenne et totale, en excluant les valeurs nulles ou négatives.

### Requête 9.4 — Top timestamps dupliqués

**Interprétation de la requête :**

Cette requête détecte les **doublons** dans la table `consumption_raw`.

Elle groupe les données par `timestamp` + `site_id`, compte le nombre d’occurrences pour chaque combinaison, et ne garde que celles qui apparaissent **plus d’une fois** (`HAVING COUNT(*) > 1`).

Elle retourne les **20 combinaisons** les plus dupliquées (timestamp + site_id), avec le nombre de fois où elles sont répétées.

```sql
SELECT TOP 20

```

**En résumé :** elle identifie les enregistrements qui sont dupliqués (même timestamp et même site), classés du plus dupliqué au moins dupliqué.

### Requête 9.5 — Corrélation météo-consommation agrégée

**Interprétation de la requête :**

Cette requête calcule une agrégation **par heure pendant toute la journée** en reliant les données de consommation et de météo.

Elle joint les deux tables sur la **même date + même heure**, ne garde que les consommations valides (`consumption_mw > 0`), puis calcule :

- `heure` : l’heure (0-23)
- `conso_moy_mw` : consommation moyenne en MW
- `temp_moy_c` : température moyenne en °C
- `vent_moy_ms` : vitesse moyenne du vent en m/s

Le résultat est trié par température moyenne croissante.



```sql
-- Agrégation par heure pour aligner les granularités (conso=15min, météo=1h)
SELECT
    DATEPART(HOUR, TRY_CAST(c.timestamp AS DATETIME2)) AS heure,
    ROUND(AVG(CAST(c.consumption_mw AS FLOAT)), 3)     AS conso_moy_mw,
    ROUND(AVG(CAST(w.temperature_c  AS FLOAT)), 2)     AS temp_moy_c,
    ROUND(AVG(CAST(w.wind_speed_ms  AS FLOAT)), 2)     AS vent_moy_ms
FROM       [Lakehouse_bronze].[bronze].[consumption_raw] c
INNER JOIN [Lakehouse_bronze].[bronze].[weather_data]    w
    ON DATEPART(HOUR, TRY_CAST(c.timestamp AS DATETIME2))
     = DATEPART(HOUR, TRY_CAST(w.timestamp AS DATETIME2))
    AND CAST(TRY_CAST(c.timestamp AS DATETIME2) AS DATE)
      = CAST(TRY_CAST(w.timestamp AS DATETIME2) AS DATE)
WHERE c.consumption_mw > 0
GROUP BY DATEPART(HOUR, TRY_CAST(c.timestamp AS DATETIME2))
ORDER BY temp_moy_c;
```

**En résumé :** elle montre la consommation moyenne et les conditions météo associées pour chaque heure de la journée, en alignant les granularités (15 min → heure).

---

### Requête 9.6 — Corrélation prix-consommation par heure

**Interprétation de la requête :**

Cette requête calcule, **par heure de la journée**, la consommation moyenne et le prix moyen de l’électricité.

Elle joint les tables `consumption_raw` et `market_prices` sur le **même timestamp** (à la seconde près), ne garde que les consommations positives, puis calcule :

- `heure` : l’heure (0-23)
- `conso_moy_mw` : consommation électrique moyenne en MW
- `prix_moy_eur_mwh` : prix moyen du marché en €/MWh

Le résultat est trié du **prix le plus élevé** au plus bas.



```sql
SELECT
    DATEPART(HOUR, TRY_CAST(p.timestamp AS DATETIME2))  AS heure,
    ROUND(AVG(CAST(c.consumption_mw  AS FLOAT)), 3)     AS conso_moy_mw,
    ROUND(AVG(CAST(p.price_eur_mwh   AS FLOAT)), 2)     AS prix_moy_eur_mwh
FROM       [Lakehouse_bronze].[bronze].[consumption_raw] c
INNER JOIN [Lakehouse_bronze].[bronze].[market_prices]   p
    ON TRY_CAST(c.timestamp AS DATETIME2) = TRY_CAST(p.timestamp AS DATETIME2)
WHERE c.consumption_mw > 0
GROUP BY DATEPART(HOUR, TRY_CAST(p.timestamp AS DATETIME2))
ORDER BY prix_moy_eur_mwh DESC;
```

**En résumé :** elle identifie les heures de la journée où l’électricité est la plus chère en moyenne, avec la consommation associée.
