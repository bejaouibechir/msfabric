# Atelier : Audit SQL et Logs dans Microsoft Fabric Warehouse – Voir précisément qui a fait quoi

Vous allez construire un atelier **Audit SQL** centré uniquement sur le **Warehouse** Microsoft Fabric :

- Activation des SQL Audit Logs (avec solution détaillée pour le bouton Save)
- Tests reproductibles entre Admin et Viewer
- Création d’une vue personnalisée `vw_audit_logs`
- Analyse fine des commandes exécutées (qui a fait quoi, quand, quelle commande ?)

Les comptes pédagogiques utilisés dans l’atelier sont :

- `participant@contactemeraudeit.onmicrosoft.com` : **Admin** (peut tout activer, créer la vue et tout analyser)
- `test@contactemeraudeit.onmicrosoft.com` : **Viewer** (accès très restreint)

Le compte `dev@contactemeraudeit.onmicrosoft.com` n’est mentionné que comme **compte d’administration du formateur** pour exécuter les manipulations qui exigent un niveau de droit élevé.

**Résultat attendu** : à la fin de l’atelier, les apprenants savent répondre à la question **« Qui a exécuté quelle commande T-SQL, quand et avec quel résultat ? »** directement dans le Warehouse.

## Partie 2 - Activer les SQL Audit Logs et préparer les données

### 2.1 - Activer les SQL Audit Logs (uniquement avec Admin) – Étapes ultra-détaillées

1. Ouvrir le Warehouse `WH_RetailCorpAuditDemo` avec `participant@contactemeraudeit.onmicrosoft.com`
2. Dans la **page du Warehouse** (éditeur SQL ouvert), cliquer sur l’icône **Settings** (engrenage ⚙️ en haut à droite)
3. Dans le panneau qui s’ouvre, dans le menu de gauche, cliquer sur **SQL audit logs**
4. Vous êtes maintenant sur la page **SQL audit logs (preview)**
5. Vérifier que le toggle **Save events to SQL audit logs** est sur **On** (vert)
6. **Si le bouton Save en bas de la page reste grisé/désactivé** (comportement fréquent en Preview) :
   - Dans la section **Log retention**, changez temporairement la valeur **Years** de 9 à **1**
   - Ou bien, dans **Events to record**, décochez la case **Select all**, attendez 1 seconde, puis recocher **Select all**
   - Ou encore, éteignez puis rallumez le toggle principal **Save events to SQL audit logs**
7. Le bouton **Save** doit maintenant devenir actif (plus grisé)
8. Cliquer sur **Save**

**Ce que vous devez voir à l’écran** :  
Le bouton Save devient cliquable, puis un message de confirmation apparaît. Le statut reste **On**.

> **Note importante** : L’interface Fabric désactive souvent le bouton Save tant qu’aucune modification n’est détectée. Une petite modification (même temporaire) est nécessaire pour l’activer.

## Partie 4 - Créer et utiliser la vue personnalisée `vw_audit_logs`

### 4.1 - Obtenir les IDs du workspace et du warehouse

1. Dans l’onglet du Warehouse, copier l’URL complète du navigateur
2. Extraire les deux GUID : `{workspaceId}` et `{warehouseId}`

### 4.2 - Créer la vue personnalisée `vw_audit_logs`

1. Avec `participant@contactemeraudeit.onmicrosoft.com`
2. Nouvelle requête SQL
3. Coller (remplacez les GUID) :

```sql
CREATE OR ALTER VIEW vw_audit_logs AS
SELECT 
    event_time,
    action_id,
    succeeded,
    server_principal_name AS utilisateur,
    statement AS commande_executee,
    session_id,
    client_ip
FROM sys.fn_get_audit_file_v2(
    'https://onelake.blob.fabric.microsoft.com/{workspaceId}/{warehouseId}/Audit/sqldbauditlogs/',
    DEFAULT, DEFAULT, DEFAULT, DEFAULT)
WHERE event_time > DATEADD(MINUTE, -60, GETUTCDATE());
GO
```

4. Exécuter

### 4.3 - Consulter la vue

```sql
SELECT * FROM vw_audit_logs
ORDER BY event_time DESC;
```

## Partie 5 - Les observations réelles (Admin vs Viewer)


Cette vue permet de voir **toute l’activité SQL** sur le warehouse  **WH_RetailCorpAuditDemo**.

### 2. Analyse des colonnes principales

| Colonne               | Signification                                                                  | Remarques                                                  |
| --------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **event_time**        | Date et heure précise de l’événement (avec millisecondes)                      | Trié par DESC → les plus récents en premier                |
| **action_id**         | Code de l’action audité (le plus important pour comprendre ce qui s’est passé) | Voir détail ci-dessous                                     |
| **succeeded**         | 1 = succès, 0 = échec                                                          | Tous à 1 ici                                               |
| **utilisateur**       | Compte qui a exécuté l’action                                                  | Ici : `participant@contactemeraudeit.onmicrosoft.com`      |
| **commande_executee** | La requête T-SQL complète exécutée                                             | Très utile pour l’investigation                            |
| **session_id**        | Identifiant de la session SQL                                                  | Permet de regrouper les actions d’une même connexion       |
| **client_ip**         | Adresse IP du client                                                           | Ici `204.43.41.207` (probablement ton poste ou un bastion) |



### 3. Décodage des **action_id** que l’on voit

| action_id | Signification       | Contexte courant                                                   |
| --------- | ------------------- | ------------------------------------------------------------------ |
| **DBL**   | **Database Logout** | Déconnexion                                                        |
| **SL**    | **SELECT**          | Lecture de données                                                 |
| **BCM**   | **Batch Completed** | Fin d’exécution d’un batch (regroupe souvent SELECT, INSERT, etc.) |

**Autres codes fréquents que tu verras probablement :**

- `AL` → ALTER
- `CR` → CREATE
- `DR` → DROP
- `EX` → EXECUTE (procédures stockées)
- `IN` → INSERT
- `UP` → UPDATE
- `DL` → DELETE

> **Note** : `BCM` est très courant quand l’audit est configuré en mode "Batch Completed Group". Il capture la fin d’exécution de presque toutes les requêtes.

- **Utilisateur unique** : `participant@contactemeraudeit.onmicrosoft.com`
- **Activité très dense** autour de **17:45:59** le 06/05/2026.
- Beaucoup de **SL** (SELECT) et **BCM** → l’utilisateur explore le schéma (`SELECT default_schema_name...`, `SELECT TOP ...`, `COALESCE`, etc.).
- Quelques **EXEC** pour configurer le contexte de session (`sp_set_session_context`).
- Des requêtes de découverte classiques (exploration des objets, limites de résultats, etc.).
- **IP constante** → même poste/client.

C’est une **activité typique d’un utilisateur qui découvre ou développe** sur le Warehouse (Power BI Desktop, DAX Studio, Azure Data Studio, ou Fabric Studio).

### 5. Intérêt Sécurité / Gouvernance

Cette vue est **très puissante** pour :

- Détecter des accès non autorisés
- Identifier qui a modifié le schéma (DDL)
- Trouver des requêtes longues ou problématiques
- Faire du forensic (qui a vu telle table ?)
- Respecter des normes comme ISO 27001, SOC2, RGPD, etc.

**Conseils de bon usage :**

1. **Filtrer intelligemment** :
   
   ```sql
   SELECT * FROM vw_audit_logs
   WHERE event_time >= DATEADD(hour, -24, GETUTCDATE())
     AND action_id IN ('SL','IN','UP','DL','AL','CR','DR')
   ORDER BY event_time DESC;
   ```

2. Créer des alertes sur les `action_id` sensibles (ALTER, DROP, GRANT, etc.) ou sur certains utilisateurs.

3. Surveiller les changements d’IP ou les connexions hors des plages horaires habituelles.

### Encore plus

Créer une vue dédiée pour l’alerte est une meilleure pratique en gouvernance et en sécurité. Cela rend la logique plus propre, plus facile à maintenir et à réutiliser.

```sql
CREATE OR ALTER VIEW vw_alert_hors_horaires
AS
SELECT 
    event_time,
    action_id,
    utilisateur,
    commande_executee,
    client_ip,
    session_id,
    succeeded
FROM vw_audit_logs
WHERE (
        -- Hors horaires de travail
        DATEPART(weekday, event_time) IN (1, 7)                    -- Samedi et Dimanche
        OR DATEPART(hour, event_time) >= 19                        -- Après 19h00
        OR DATEPART(hour, event_time) < 8                          -- Avant 08h00
      )
  AND action_id IN ('UP', 'DL', 'IN', 'AL', 'CR', 'DR', 'EX', 'SL')  -- Actions sensibles + SELECT
  -- AND utilisateur <> 'participant@contactemeraudeit.onmicrosoft.com'  -- Décommente si tu veux exclure ton compte
;
```

> Astuce :r les horaires (19 et 8) selon tes vrais horaires de travail.

Une fois la vue créée :
Dans l’éditeur SQL, exécute cette requête simple :

```sql
SELECT * 
FROM vw_alert_hors_horaires
WHERE event_time >= DATEADD(minute, -10, GETUTCDATE())   -- dernières 10 minutes
ORDER BY event_time DESC;
```

Clique sur le bouton "Create rule" (en haut).
Configure la règle comme suit :

Rule name : Alerte - Activité Hors Horaires
Query : La requête ci-dessus (SELECT * FROM vw_alert_hors_horaires WHERE ...)
Run query every : 5 minutes
Condition : On each event
Action : Message to individuals → Participant (et ajoute  email si besoin)
